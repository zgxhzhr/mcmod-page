### 6.1.9 通用文本：用一条「文本类资料」承接整族重复正文

重复条目的**首选解法**。比留空等抽象类更直接——通用文本本身就是一条正式资料，
其余条目在附言里引用它，读者从任一页都能跳过去看完整说明。

#### 怎么建这条通用文本

| 字段 | 填什么 |
|---|---|
| 主要名称 | 抽象名，如「食物」 |
| 次要名称 | 对应英文，如 `Food` |
| 资料类型 | **物品/方块** |
| 资料分类 | **`{文本}`**（下拉选「自定义」，输入框里填大括号包住的「文本」）|
| 正文 | 这一族**共通的**说明：是什么、从哪来、怎么用 |

`{文本}` 是站上约定的分类名，不是占位符——按原样输入。

#### 其余条目怎么写

正文**只留这条自己独有的数据**，共通的部分不再重复：

```html
<!-- 代表页（通用文本）的正文 -->
<p>这些物品是模组中的食物。获取：从民用战利品、稀有民用战利品、医疗战利品、
警用战利品与军用战利品等容器中搜到，也可以在创造模式的物品栏里直接取得。</p>

<!-- 其余条目的正文：只写数值 -->
<p><strong>属性</strong>：[icon:hunger-level=4,点]饥饿值、[icon:saturation-level=1.2,点]饱和度。</p>
```

**附言里写明引用关系**：

```
Crafting Dead: Survival 资料页：中文名取自 lang/zh_cn.json。
本条正文仅列出该物品的独有数据，通用说明需引用通用文本「食物」。辛苦喵呜机了
```

#### 和另外两条路的取舍

| 方案 | 适用 | 代价 |
|---|---|---|
| **通用文本**（本节）| 一族物品有明确共性，条目数中等 | 建 1 条额外资料；条目正文要拆成「独有数据」 |
| 留空 + 请求抽象类（§6.2.2.5）| 数量大、共性弱、站方需要建结构 | 读者点进去是空页，体验差 |
| 拆包交 IRR（§6.2.0）| 超过 100 条、极高重复 | 要交给百科团队，流程长 |

**优先级：能建通用文本就建通用文本。** 它不依赖站方动作，也不用拆包，
是目前代价最低、读者体验最好的做法。留空请求抽象类留给「实在说不出共性」的情况。

#### 踩过的坑

Crafting Dead: Survival（4397）的 70 条食物，有 8 种正文结构，其中 43 条完全同构。
最初 46 条都写了正文，等于把同一段话复制了 40 多遍。正解是建「食物」「饮品」「容器」
三条通用文本，其余条目只写数值。

### 6.1.10 合并 / 综合 / 引用通用文本 —— 三类功能的官方判定表

**出处**：<https://bbs.mcmod.cn/thread-4674-1-1.html>（转述主站编辑规范第 33 条）

> 33. 在多个同类资料的相互文本重复率较高时，**必须**使用「综合」功能创建父资料，
> 或创建隐藏文本资料后「引用」。

#### 三条硬边界

| | 合并 | 综合 | 引用通用文本 |
|---|---|---|---|
| **构成** | 1 个父资料 + 1~多个子资料 | 1 个**抽象**父资料 + 多个子资料 | 1 个或多个**隐藏资料** + 多个**任意**资料 |
| **子资料数量** | **最少 1，最多不宜超过 10** | **最少 2，最多不宜超过 450** | 无上限 |
| **用途** | 同一页面展示多个**互相有关系**的物品 | 多个**介绍几乎完全一样**的物品汇总到父资料 | 多个介绍几乎完全一样的**部分文本**汇总到隐藏资料 |
| **目的** | 对父资料的**引申与扩展阅读** | 避免复制粘贴相同内容 | 避免重复 + 保持各资料可塑性 |
| **列表显示** | 嵌套 | **轮播**（子资料正文**只会固定引用父资料**）| 与普通资料一样 |
| **典型例子** | 碳板 -(碳纤维、碳网)<br>污水 -(污水桶)<br>星辰剑 -(沾满尘土的星辰剑) | 彩色玻璃 -(橙/白/蓝色玻璃…)<br>钢套装 -(钢头盔、钢胸甲…)<br>镐头部件 -(燧石/铁/金/钻石镐头…)<br>大理石装饰方块 -(大理石、大理石楼梯…) | 锡锭、铅锭 与「锭」<br>进阶流体提取机 V/VI 与「进阶流体提取机」 |

#### 怎么选（按顺序问）

```
1. 子条目之间是「派生 / 引申」关系（A 能变成 B、B 是 A 的一种）？
   是 → 合并（且子条目 ≤ 10）
   否 → 下一步

2. 整页正文是否「几乎完全一样」，逐条写等于复制粘贴？
   是 → 综合（子条目 2~450）
        └ 例外：若父资料会因此过于庞大 → 引用通用文本
   否 → 下一步

3. 是否只有「某几段」（部分文本）重复，各条还有自己的独有内容？
   是 → 引用通用文本
```

**官方明确留了口子**：

> 以上适用场景仅为示范，编辑者可**视模组内的实际情况**，使用现有功能组成适合介绍中场景的方案。
> 最终达到使玩家方便理解各物品的用途、降低资料重复率的目的即可。

所以不必机械对号，**核心指标是「降低重复率 + 让玩家看懂」**。

#### 「综合」的坑（官方特别警告）

> 使用综合功能时，若子资料内有文本则**需慎重处理**，在综合时需要将**有用的内容移动至父资料**中，
> **最好先把父资料写好后再使用综合**，否则会导致原本有内容的资料无法查看。

所以流程必须是：**先写父资料 → 提交 → 综合 → 子资料正文清空**。
不要先提交 49 条有正文的子资料再申请综合，那样正文会丢。

#### 非编辑员怎么提交

> 非编辑员处理这类资料时，需在附言中说明需要协助的操作，或在提交前联系编辑员或管理员。
> 由于非编辑员不能进入后台，或因用户组限制不能跨区域进行后台编辑，故无法使用 合并 / 综合 / 引用 的功能。
> 本贴用于提交这些功能的操作申请，管理会根据情况协助完成相应的工作。

**申请格式**（写进给审核员的话术里）：

```
功能：合并
父资料：（资料 URL 链接）
子资料：（资料 URL 链接）
```

```
功能：综合
抽象父资料：（有则贴上资料 URL 链接，无则忽略，交由管理来创建）
子资料：（资料 URL 链接）
```

```
功能：引用通用文本
引用的文本：（有则贴上资料 URL 链接，无则忽略，交由管理来创建）
需要引用的资料：（资料 URL 链接）
```

#### ⚠️ 这三类功能只减正文，不减图标

**图标永远逐条给**，与用哪种方案无关。

实测教训（Factory Blocks 20843）：49 个方块按「综合」交付，子资料 `html` 留空、
等站方引用父资料——但**子资料的 `icon32` / `icon128` 必须各自渲染**，
因为每个变体的纹理不同，合并不了。

同理，通用文本方案里「正文留空」的条目，图标照样要单独出。

#### 本机已有的实现方式对照

| 方案 | 我们这边的做法 | 产出文件命名 |
|---|---|---|
| 合并 | 父页正文 + 子页各自正文（子页写自己的差异）| `<mod>-父页-<id>.json` + `<mod>-子页-<id>.json` |
| 综合 | 父页写全套说明，子页 `html` 留空、`remark` 注明「正文由父资料统一提供」| `<mod>-父资料-<id>.json` + `<mod>-子资料-<id>.json` |
| 引用通用文本 | 隐藏文本页 `category = {文本}`，各条 `remark` 里写「通用说明需引用通用文本「X」」| `<mod>-通用文本-<id>.json` |

#### 实测案例

| 模组 | 条目 | 判断 | 依据 |
|---|---|---|---|
| Nemo's Carpentry 31737 | 632 方块，50 种造型 × 12 木材 | **引用通用文本**（5 条）+ A/B 拆包 | 只有「造型说明」部分重复，各条还有木材差异 |
| Crafting Dead 4397 | 70 食物 | **引用通用文本**（4 条）| 只有共通说明重复 |
| RE 24724 | 81 物品 | **引用通用文本**（11 条）| 按化学品/装药/流体等分组，组内重复 |
| Simple Wooden Pipes 15375 | 8 管道 | **引用通用文本**（1 条）| 75% 正文重复，但只 8 条、不足综合的规模 |
| Factory Blocks 20843 | 49 方块，全部同名「工厂方块」 | **综合**（1 父 + 49 子）| 主名相同、属性全同（复制铁块）、整页正文都会重复 |

**判据小结**：条目**少**（< 10）且只是部分重复 → 通用文本；条目**多**（≥ 10）且整页重复 → 综合。

### 6.1.11 抽象资料怎么建：两步，自己就能做

「综合」不是等管理员帮你操作——**抽象资料就是一条普通的新增资料，只是内容形式特殊**。
两步走：

#### 第一步：先提交抽象资料

| 字段 | 怎么填 |
|---|---|
| **主要名称** | 按被综合的那批资料起名，如「XX套装」/「XX Suit」 |
| **正文** | 填这套东西的整体介绍（机制、共同属性、合成方式） |
| **图标** | **留空**（游戏里不存在这个东西）|
| **注册名** | **留空** |
| 分类 / 类型 | 按被综合的物品填（建筑方块 / 物品·方块 等）|

#### 第二步：逐个添加真实物品

| 字段 | 怎么填 |
|---|---|
| **正文** | **不填**（会自动引用抽象资料）|
| 其它字段 | 正常填（名称、注册名、图标、堆叠上限…）|

#### 为什么这样设计

> 抽象资料是一个虚拟的资料，在游戏里不是真实存在，它只用来综合描述多个真实物品，
> 避免在多个真实物品内反复介绍相同的内容。

所以它**没有图标、没有注册名**——这两项都必须留空，不然读者会以为游戏里真有个叫这名字的东西。

#### 关键判断：什么情况能走这条路

**前提是：各条真实物品之间没有独有数据要显示。**

| 适合 | 不适合 |
|---|---|
| 49 个同名「工厂方块」，只有纹理不同 | 22 个罐装食品，每件饥饿值不同（数值必须各自显示）|
| 21 个遮阳棚，形状完全一致 | 19 件饰品，每件效果不同 |
| 同一套盔甲的各个部件 | 同一族但每件带独有属性的武器 |

**有独有数值时不要走抽象资料**，否则这些数值没有地方放——正文空着，读者查不到某件具体物品的数据。
这种情况用【引用通用文本】（§6.1.9）或「全部走 IRR」（§6.2.0）。

#### 与我们已有交付的对应

| 模组 | 抽象资料 | 子资料（正文空）|
|---|---|---|
| Factory Blocks 20843 | 「工厂方块 / Factory Block」 | 49 个方块 |
| Exline's Awnings 28508 | 「遮阳棚 / Awning」 | 21 个遮阳棚 |

⚠️ **这两批的父资料当时都填了图标，按本标准应该留空**，需要修正。

### 6.1.11.1 抽象资料的典型用法：一张表把所有差异列完

审核对这类页面的退回理由**几乎一字不差**，见过三种说法：

> 这一类一种设备的不同电压的版本，创建综合抽象资料用一个表列出区别就可以啦

> 用综合，抽象资料内用一个表格把不同的效果、种植条件列出来就可以了

#### 判据：差异能不能列成一张表

```
这个族里的每一条，功能说明是不是完全一样？
  ├─ 是 → 差异能不能用 1~3 列表达？
  │        ├─ 能 → 抽象资料 + 一张表（本节）
  │        └─ 不能 → 拆成「引用通用文本」，各条保留自己的段落
  └─ 否 → 各条差异太大，走普通逐条提交
```

**最快的自检**：把各条正文并排看，相同段落是不是超过 80%。
超过就是该综合了，别一条条交。

#### 表格怎么设计

- **首列**是被综合各条的名字（电压等级 / 浆果名 / 材质）
- **中间列**是差异维度（数值、效果、条件）
- **共性写进正文**，不要塞进表格重复 N 遍

实例（GregTech Energistics 5175，8 个 AE2 库存覆盖板）：

```
正文（写一遍）：
  用法：贴在格雷机器的任意一面，接入 ME 网络后配置合成样板…
  库存机制：持续监测机器内的材料量，低于设定值即补充…
  状态显示：界面显示运行中、缺少样板、网格连接异常…
  开关：流体支持与输出功能可单独开关…

表格（8 行）：
  | 等级 | 最大库存   | 相对 LV |
  | LV   | 1,280     | 1×     |
  | MV   | 5,120     | 4×     |
  | HV   | 20,480    | 16×    |
  | …    | …         | …      |
  | UV   | 20,971,520| 16384× |
```

**注意「相对 LV」这一列是后加的**——原始数据只有绝对数值 1,280 / 5,120 / 20,480…，
读者看不出规律；换成 1×/4×/16× 一眼就能看出「每级四倍」。
**能算出比例关系的，就把比例也列一列。**

实例（Strange Berries 17728，16 种浆果）：

```
正文（写一遍）：种植分四阶段、采摘 1~2 颗、踩踏给效果且村民狐狸免疫…

表格（16 行，四列都是差异）：
  | 浆果              | 饥饿值 | 饱和度 | 食用效果       | 可种植于        |
  | Speed Berries     | 1     | 1     | 速度 II（10秒）| 草方块、泥土、粗土 |
  | Night Berries     | 1     | 1     | 夜视 I（20秒） | 草方块、泥土、粗土、灰化土 |
  | Golden Berries    | 4     | 2     | 伤害吸收 I…    | 仅金块          |
```

#### 反面写法（会被退）

把共性复制到每一条里，只改一个数字：

```
✗ AE2 库存覆盖板（LV）是…八级中的 LV 档。
    最大库存：1,280。
    用法：贴在格雷机器的任意一面…      ← 8 条一字不差
    库存机制：持续监测…                ← 8 条一字不差
    状态显示：界面显示运行中…           ← 8 条一字不差

✓ 抽象资料里这四段各写一遍，8 条子资料正文留空
```

#### 子资料正文留空后，还有什么要填

| 字段 | 填什么 |
|---|---|
| 名称 | 完整名称（要能区分，如「AE2 库存覆盖板（LV）」）|
| 注册名 | 各自的注册表 id |
| 图标 | **各自渲染，不能省**（§6.1.11 末尾那条）|
| 分类 / 类型 | 正常填 |
| 正文 | **空** |

#### 已用这条路线的模组

| 模组 | 抽象资料 | 子资料 | 表格内容 |
|---|---|---|---|
| Factory Blocks 20843 | 工厂方块 | 49 | 无表（各条只是纹理不同）|
| Exline's Awnings 28508 | 遮阳棚 | 21 | 无表（形状完全一致）|
| More Slab 8830 | 台阶 | 151 | 分类统计表 |
| Strange Berries 17728 | 奇异浆果 | 32 | 16 行 × 4 列 |

### 6.2.0 大批量重复条目的交付拆分：我们提交代表页，剩余交 IRR 格式给百科团队

**适用条件（三个同时满足）**：

1. 同一类物品 **超过 100 个**；
2. 正文/属性**大量重复**（归一化后只剩少数几种结构）；
3. 制作方认可**可以建抽象资料**（属性完全一致、只有外观或数值不同的族类）。

满足时不要硬着头皮提交几百条几乎一样的页面，分成两包：

| 包 | 格式 | 内容 | 谁提交 |
|---|---|---|---|
| A | **我们的批量 JSON**（`id/name/ename/regname/...`）| 每类**代表页** + 确实有独特内容的页 | 我们自己批量提交 |
| B | **IRR 格式 JSON**（`name/englishName/registerName/smallIcon/largeIcon/...`）| 剩下的重复条目 | 交百科团队批量导入 |

**为什么这样分**：几百条同结构的页面我们自己提交，只是把「重复」从一个地方搬到另一个地方；
真正的解法是**建抽象资料**，让站方用一个模板覆盖整族。我们负责把代表页写好、把抽象类需求说清楚，
其余条目以站方能直接吃的格式交过去。

**B 包（IRR 格式）的生成要求**：

```python
# 每行一个 JSON 对象（JSONL），不是数组
{
  "name": "冰红茶",                    # 中文名
  "englishName": "Iced Tea",          # 英文名（标题格式，不是注册名写法）
  "registerName": "modid:iced_tea",   # 完整注册名
  "TagList": None,                    # 物品标签，没有就 None
  "CreativeTabName": None,            # 创造标签页，不知道就 None
  "type": "Item",                     # Item / Block
  "maxStackSize": 1,
  "maxDurability": 0,
  "smallIcon": "<base64 PNG>",
  "largeIcon": "<base64 PNG>"         # 128×128
}
```

- 图标**必须 128×128**（IRR 的 FBO 就是这个尺寸）
- base64 **不带 `data:` 前缀**
- `type`：能转成方块记 `Block`，否则 `Item`
- 文件名 `export/<modid>_item.json`，实体是 `<modid>_mob.json`

**A 包（我们的格式）交什么**：

- 每类的代表页，正文写全（属性、获取、用法），其余同族条目的正文留空并写
  「需协助创建抽象类」——这部分和 §6.2.2.5 的做法一致；
- 如果某条有独特信息（限定版、变质版、有特殊效果），单独留一条正文，不要并进模板。

**不适用的情况**：物品不到 100 个，或者重复度不高（每组只有两三条）→ 全部走我们的格式逐条提交，
不值得拆包，多一个格式反而增加对不齐的风险。

#### 附：IRR 官方导出格式（参考，不是我们的交付格式）

`IRR-1.0-1.16.X.jar`（cn.mcmod.item_render）是 mcmod 官方的图标导出模组，
它的 JSON 是站方自己认的格式。**我们批量脚本吃的是另一套字段**，两者不要混。

##### 物品：`export/<modid>_item.json`

**字段表由 `javap -p` 反汇编 ItemData.class 确认（10 个字段 + 1 个 transient）**：

```
public String name;              ← zh_cn 环境下的显示名
public String englishName;       ← en_us 环境下的显示名
public String registerName;      ← getRegistryName().toString()
public String TagList;           ← getTags().toString()，等于 "[]" 时置 null
public String CreativeTabName;   ← 创造标签页名，可能 null
public String type;              ← "Block" / "Item"
public int    maxStackSize;      ← getMaxStackSize()
public int    maxDurability;     ← getMaxDamage() + 1   ← 注意 +1
public String smallIcon;         ← base64 PNG
public String largeIcon;         ← base64 PNG
private transient ItemStack itemStack;   ← 不序列化
```

**三个容易写错的点**：

1. **`maxDurability` 是 `getMaxDamage() + 1`**。无耐久物品的 `getMaxDamage()` 是 0，
   所以导出值是 **1，不是 0**。
2. **null 字段不出现**。`new GsonBuilder().disableHtmlEscaping().create()` 没调 `serializeNulls()`，
   所以 `TagList` / `CreativeTabName` 为空时**整个字段被省略**，不要显式写 `null`。
3. **`name` 与 `englishName` 是两次语言环境切换后各取一次**：
   ```java
   refreshLanguage(mc, "zh_cn");  setName(getDisplayName());   // 中文名
   refreshLanguage(mc, "en_us");  setEnglishName(getDisplayName());  // 英文名
   ```
   模组没有中文语言文件时，zh_cn 回退到 en_us，两者相同——这是对的。



**JSONL 格式——每行一个 JSON 对象，不是数组。**

```json
{"name":"水瓶","englishName":"Water Bottle","registerName":"craftingdeadsurvival:water_bottle","TagList":null,"CreativeTabName":"...","type":"Item","maxStackSize":3,"maxDurability":0,"smallIcon":"<base64>","largeIcon":"<base64>"}
```

| IRR 字段 | 含义 | 我们对应 |
|---|---|---|
| `name` | 中文名 | `name` |
| `englishName` | 英文名 | `ename` |
| `registerName` | 注册名 | `regname` |
| `TagList` | 物品标签（字符串化数组，空为 `null`）| 无 |
| `CreativeTabName` | 创造模式标签页 | 无 |
| `type` | `"Block"` 或 `"Item"` | `type`（值不同：我们用「物品/方块」）|
| `maxStackSize` | 最大堆叠 | `maxstack` |
| `maxDurability` | 最大耐久 | 无 |
| `smallIcon` | 小图标 base64 | `icon32` |
| `largeIcon` | 大图标 base64 | `icon128` |

##### 实体：`export/<modid>_mob.json`

```json
{"name":"侦察兵僵尸","Englishname":"Scout Zombie","mod":"scout_zombie","registerName":"craftingdeadsurvival:scout_zombie","Icon":"<base64>"}
```

| 字段 | 含义 |
|---|---|
| `name` | 中文名 |
| `Englishname` | 英文名（**首字母大写 E，与物品的 `englishName` 不一致**）|
| `mod` | 注册名的 path 部分 |
| `registerName` | 完整注册名 |
| `Icon` | 实体图标 base64（**首字母大写 I**）|

##### 图标的三个硬事实

1. **固定 128×128**。`FBOHelper.renderTextureSize = 128`，FBO 就是这个尺寸，没有 32×32 版本。
2. **纯 PNG 的 base64，无 `data:` 前缀**。`ImageIO.write(image, "PNG", out)` 后 `Base64.encodeBase64String`。
3. **实体图标要垂直翻转**（`getBase64(true)`），物品不翻（`getBase64(false)`）——GL 纹理坐标原点在左下。

##### `type` 的判定

```java
Block.getBlockFromItem(item) != Blocks.AIR ? "Block" : "Item"
```

能转成方块的记 `"Block"`，否则 `"Item"`。**这个二分法比我们的「物品/方块」粗**——
台阶、门这类既算方块又有物品形态的，IRR 一律记 `"Block"`。

##### 要不要改用 IRR 格式

**不改。** 我们的批量脚本走的是页面注入（填表单），字段直接对应页面控件
（`#icon-32x` / `#icon-128x` / `ename` / `regname`），和 IRR 的导出文件是两条路。
IRR 格式的价值在于：它能证明**站方确实要求「小图标 + 大图标」两张图**，
以及大图标的标准尺寸就是 **128×128**——这一点和 §6.7.1 的要求一致。

### 6.6 批量新增资料（装一次，之后打开页面就能用）

逐条手填太慢时用这套：**浏览器扩展常驻注入 + 从源码生成数据**。装完后打开任意 `/item/add/<classId>/` 页面，工具栏「读取 (Ctrl+O)」后面会多一个 **批量新增** 按钮，选数据文件即可自动跑。

**三个文件（本包 `scripts/` 下）**

| 文件 | 作用 |
|---|---|
| `mcmod-batch.user.js` | 页面注入脚本：注入按钮 + 面板，逐条填表并提交 |
| `install-batch-extension.ps1` | 把它装成 Edge/Chrome 的「加载解压缩的扩展」，之后自动生效（无需书签、无需控制台） |
| `gen-items.py` | 从模组源码生成 `items.json`（扫纹理 + 读 lang + 纹理放大成 32×32 base64） |

> 维护提醒：本包里的 `.ps1` **必须存成「UTF-8 带 BOM」**。PowerShell 5.1 读无 BOM 的 UTF-8 会把中文当 GBK 解，直接语法报错——这是这套脚本最容易踩的坑。

**安装（一次）**

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install-batch-extension.ps1
# 然后 edge://extensions → 开发人员模式 → 加载解压缩的扩展 → 选屏幕提示的目录
```

**生成数据**

```powershell
python scripts\gen-items.py --assets "<mod>/src/main/resources/assets/<ns>" --namespace <ns> `
    --category "<资料分类>" --maxstack 1 --out items.json
```

`items.json` 每条字段：

| 字段 | 含义 | 备注 |
|---|---|---|
| `name` / `ename` | 主要 / 次要名称 | 从 lang 取，别从代码标识符翻译（§6.2） |
| `regname` | 注册名 | `<ns>:<id>` |
| `category` | 资料分类 | 已有同名直接选，没有就自定义新建；留空则不动 |
| `type` | 资料类型 | 默认「物品/方块」 |
| `maxstack` / `damage` / `oredict` | 数值字段 | **不要给元数据填 0**，会报「只能输入 1 到 2147483647 之间的正整数」 |
| `html` | 正文 | 必须写功能（§6.4） |
| `icon32` | 小图标 base64 | **裸 base64，不要 `data:` 前缀**（页面自己补）；大图标靠「同步至大图标」生成 |
| `remark` | 改动附言 | 写清楚批次，审核员好认 |

**脚本的确定性顺序**（缺一步就填不上，别自己改顺序）：

1. 先选**资料类型**（`.common-item-mold-list li a`）——不选它，「资料分类」的下拉根本不在 DOM 里；
2. 再选资料分类（`#item-type-select` + `#item-type-custom`）；
3. 填名称 / 注册名 / 堆叠 / 耐久 / 附言（`[data-multi-id="..."]`，必须**原生 setter + input/change 事件**）；
4. 写 `#icon-32x-editor` 与 `#icon-32x`，再点「同步至大图标」；
5. 正文走 CodeMirror（`.CodeMirror` 元素上的 `.CodeMirror.setValue(html)`）；
6. 提交 `#edit-submit-button` → 弹「资料添加确认」→ 点「确定提交」。

**提交弹窗怎么读**：分「错误（必须改）/ 警告 / 提示（可以忽略）」。**错误必须清零**；警告里「疑似第一人称/主观」「疑似不规范/错词」在引用作者原文（lore 含「我们」）时是**误报**，可以忽略。获取方式写不出真实途径时，正文据实写「仅创造模式可获取 / 生存获取途径待确认」，站点自己的提示也认可这种写法。

**中断与续跑**：进度存在 localStorage，**按 classId 分开但不按文件分开**——这一条踩过坑：跑完批次 1（6 条）后再载入批次 2（7 条），脚本会从第 7 条开始，结果只跑了 1 条。所以正确的做法是**按 `regname` 去重**：载入文件时进度归零，跑批时凡是 `state.done` 里已有的 `regname` 一律跳过（v2.1 已实现）。「暂停」立即生效。

**两个配套机制（v2.3+）**：

- `force: true`：某条在站点上被**撤回**后要重发时用。本机 `done` 里还留着它的 `regname`，不加 `force` 会被当"已提交"跳过。
- 面板**「重置」**：清空本机 `done`。**站点被清空/大量撤回后必须点一次**，否则脚本会以为全提交过、整批跳过（"全跳过"就是这么来的）。重置不影响站点上的资料。
#### 两次踩过的注入脚本维护坑

**坑 1：同一脚本不能有两个来源。**

装了 Edge 扩展就不要再在 Tampermonkey 里留同一份。两个实例都用 `#mb-*` 做面板 id，
会互相移除对方的面板，表现为「版本号不对」「面板闪一下又变回旧的」。

排查：Tampermonkey 管理面板里搜 `批量新增`，有就删。扩展目录在
`%LOCALAPPDATA%\McmodBatchExt`，Tampermonkey 的脚本存在
`%LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Local Extension Settings\dhdgffkk...`（LevelDB，
可以 grep 到 `@name` / `@version` / `MB_VERSION`）。

**坑 2：加新面板必须同步加进两个清理列表。**

脚本里有两处「移除旧面板」的检查，都是硬编码的面板 id 数组：

```js
// 第 42 行左右：removeStalePanels()
// 第 125 行左右：window.__mbBatchLoaded 接管检查
['mb-panel', 'mb-list-panel', 'mb-edit-panel']
```

**新增面板时漏加这个数组**，那个面板就永远不会被新版本接管——旧面板一直挂着，
表现为「扩展已经是 2.34，面板还显示 2.33」。

2026-11 就踩过：`mb-verify-panel`（审核列表）和 `mb-addq-panel`（新增队列）没进数组，
审核列表页永远显示旧面板。v2.35 才补全成 5 个 id。

**改完脚本必须做的两件事：**

1. **升版本号**，三处都要改：`@version`、`const MB_VERSION`、扩展的 `manifest.json`；
2. **同步到扩展目录** `%LOCALAPPDATA%\McmodBatchExt\content.js`，然后
   `edge://extensions` 点刷新——**浏览器加载的是那个副本，不是包里的 `.user.js`**。

#### 无图标的条目也要勾「删除大小图标」（脚本 v2.39 起）

「删除大图标 / 删除小图标」这两个勾选框必须与图标状态保持一致：

| 有图标 | 勾选框 |
|---|---|
| 有 | **不勾**（勾了会把刚填的图标删掉）|
| 无 | **勾上两个**（不勾会留下上一张的残留）|

**踩过的坑（脚本 v2.38 及之前）**：

```javascript
if (it.icon32 || it.icon128) syncIconDeleteBoxes(!!it.icon32, !!it.icon128);
```

只有「有图标」时才进这个分支，**无图标的条目根本不会去动勾选框**。于是自然生成、
游戏设定、实体这些本来就没图标的类型，提交时两个勾选框是空的，被审核挑出
「大小图标应该勾选删除」。

v2.39 起改成无条件调用：

```javascript
syncIconDeleteBoxes(!!it.icon32, !!it.icon128);   // 有图标→取消勾选，无图标→勾上
```

函数内部的判断是 `wantDeleted = !hasIcon`，所以传全 false 就等于「勾上两个」。

### 写法

**每类只保留第一条的正文**，其余条目的 `html` 留空，`remark` 分两种措辞：

```python
_seen = set()

def add(key, category, html):
    if category in _seen:
        html = ""
        note = (f"同类物品的正文已集中在「{category}」类的首条页面，本条留空，"
                "需协助创建抽象类以统一展示。")
    else:
        _seen.add(category)
        note = f"本条为「{category}」类的正文代表页，同类其余条目留空并引用同一套说明。"
    ...
```

### 附言里要明确请求管理员

**留空的那条必须写清「需协助创建抽象类」**，否则审核只看到「正文空白」，
会当成没写完整再退回一次。要让管理员知道这是有意的、并且需要他配合建抽象页。

| 条目 | remark 里写 |
|---|---|
| 同类首条（有正文）| 本条为该类的正文代表页，同类其余条目留空并引用同一套说明 |
| 同类其余（正文空）| 正文已集中在首条页面，本条留空，需协助创建抽象类以统一展示 |

### 什么时候不该合并

同类条目如果**机制真的不同**，就不要合并。例如机器的加热器与电解机各有各的作用，
反应容器更是整条生产线的核心——这种应该分开写，哪怕数量少。

判断标准：把两条的正文对调，如果读起来都不违和，说明可以合并。

#### 批量编辑 JSON 的字段白名单（只有 5 个）

编辑已有页面时，**批量编辑 JSON 只认五个字段**，多一个都会被当成脏数据：

```json
{
  "id": "926635",
  "name": "缓冲器",
  "editRemark": "补全正文：…辛苦喵呜机了",
  "editNote": "补全正文：Buffer 的作用、用法与限制。",
  "html": "<p>…</p>"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 资料页数字 id，不是 verifyId |
| `name` | 是 | 页面名称，用于核对 |
| `editRemark` | 是 | 改动附言，结尾「辛苦 XXX 机了」 |
| `editNote` | 是 | 修改说明，一两句 |
| `html` | 是 | 正文 |

**不要带这些**：`ename`、`regname`、`category`、`type`、`maxstack`、`icon32`、`icon128`、`remark`
——它们是**新增 JSON**（`<模组>-物品导入-<classId>.json`）的字段。编辑时页面已经存在，
这些元数据不该被覆盖；混进来会让脚本按新增流程处理，或者把已有字段洗掉。

两套 JSON 别搞混：

```
-物品导入-<id>.json   新增 → id/name/ename/regname/category/type/maxstack/remark/html/icon32
-编辑-<id>.json       编辑 → id/name/editRemark/editNote/html
-方块导入-<id>.json   新增 → 同上，category 用「方块」「结构标记」等
-实体导入-<id>.json   新增 → 同上，实体 icon32 留空
```

**踩过的坑**：TubeStuff（646）那批 23 页第一次提交时带了 `ename` 和 `icon32`，
文件从 16 KB 涨到 36 KB，全是无用数据。

#### 审核中条目的修正：用 verifyId，不是 id

提交后还在「审核中」的条目没有资料 id（`id` 为 null），要改它得走**再编辑**路径：

```
/item/add/<classId>-<verifyId>/
```

比如 `4397` 模组的第 `817550` 号审核项 → `/item/add/4397-817550/`。

**数据格式**（批量脚本 v2.6 起支持）：

```json
{
  "kind": "新增",
  "verifyId": 817550,
  "name": "空水壶",
  "ename": "empty_water_canteen",
  "regname": "craftingdeadsurvival:empty_water_canteen",
  "category": "食物",
  "type": "物品/方块",
  "maxstack": 3,
  "html": "…",
  "icon32": "…",
  "remark": "…辛苦喵呜机了"
}
```

脚本按 `kind === '新增' && verifyId` 判断落地页，跳到 `/item/add/<classId>-<verifyId>/`；
没有 `verifyId` 才走 `/item/edit/<id>/`。

**从审核列表导出 JSON 的字段**：

| 字段 | 用途 |
|---|---|
| `verifyId` | 拼再编辑 URL |
| `name` | 形如 `空水壶 (empty_water_canteen)`，**要去掉括号里的注册名**才能对上数据 |
| `kindLabel` | `物品/方块` / `生物/实体`，用来区分要不要补图标 |
| `status` | `审核中` / `已撤回`，已撤回的一般跳过 |

> **关键：修正数据必须给全量字段。** 新增模式的 `fillOne` 用 `clearOrSet` 处理 ename / regname /
> maxstack / damage / oredict——**没给就清空**。只写 `{verifyId, icon32}` 会把名称之外的所有字段洗掉。
> 正文 `html` 是例外（只在有值时写），但为了保险也一起带上。

**只补图标这一类修正**的写法规矩：把原数据的全部字段照抄，只替换 `icon32`，`remark` 写清原因
（「上一条提交时为删除图标勾选状态，导致图标被清除，本次内容一致只补回图标」）。

### 6.9 注入脚本的实战坑（面板 / 按钮 / 样式）

**别再靠 MCP 坐标点击驱动浏览器。** 每产生一次工具结果，客户端窗口就会抢前台，Setyp 按键落到哪个窗口不可控——实测出现过「点进聊天框」「网址打到错标签」。正确做法是**把逻辑注入页面**（浏览器扩展 / 油猴 / 控制台），人只点一次按钮。

**按钮锚点**：

- 只能用**页面原生元素**做锚点。曾用工具栏的「实用工具」复选框做锚点，结果那个复选框是 **Mcmodder 注入的**，换个环境就没了；
- 更致命的是**轮询时机**：脚本在 `document-idle` 就跑，编辑器工具栏还没渲染时，会先匹配到**顶部导航**里的同名「实用工具」，把按钮插到站点头部去。所以注入前必须**先确认锚点所在容器已存在**（如先等到「读取 (Ctrl+O)」按钮），等不到就继续轮询（30 秒上限）。
- 兜底锚点用「批量导入：《如何批量添加资料》」这类**长期存在的原生链接**。

**面板样式**：站点 CSS 会覆盖你 popup 里的颜色与字号（深底 + 深字 = 看不见）。做法：

- 样式单独用 `<style id="mb-style">` 注入，关键属性一律 `!important`；
- 字号不要低于 13px（操作面板）／12.5px（日志）；日志区用等宽字体 + 深底亮字；
- 用 `id` 而不是 class，避免和站点样式撞车。

**改脚本本身**：PowerShell 的 here-string 里塞多行 JS 极易被引号/换行破坏（踩过，产出一个语法错误的文件）。**用 Python 读写文件做字符串替换**更稳，改完必须跑 `node --check`。
