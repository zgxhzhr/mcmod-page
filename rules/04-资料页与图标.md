### 6.2.2.4 主要名称与次要名称怎么填

资料页有两个名称字段：

| 字段 | 对应站上位置 |
|---|---|
| `name` | 主要名称（资料页标题） |
| `ename` | 次要名称（标题下方的英文行） |

**填法只看模组有没有中文语言文件**：

| 模组语言文件 | `name` | `ename` |
|---|---|---|
| 有 `zh_cn.json` / `zh_CN.lang` | 中文名 | 英文名 |
| 只有 `en_us`（无中文） | 英文名 | **留空** |

**没有中文时不要两个都填英文。** 次要名称本来就是给「中文名 + 英文原名」这种对照用的，
两个都填英文等于把同一个词写两遍，页面上会出现两行一样的标题。

```json
// ✓ 有中文
{ "name": "莱泽尔太阳能电池", "ename": "Litherite Solar Cell" }

// ✓ 无中文：英文名当主名，次要名称空着
{ "name": "Acetone", "ename": "" }

// ✗ 无中文却两个都填
{ "name": "Acetone", "ename": "Acetone" }
```

`ename` 字段本身要保留（写 `""`），不要整个删掉——批量脚本按字段存在与否决定是否写这一栏。

**繁体中文算中文**。模组只提供 `zh_tw.json` 时，主名称用繁体的简体写法（如「岩石使者娃娃」），
次要名称填英文名。

**踩过的坑**：Realistic Explosives（24724）103 条一开始把 `name` 和 `ename` 都填了英文，
等于每页标题下方重复一遍同样的词。

#### `ename` 的写法：标题格式，不用注册名

**次要名称一律「每个词首字母大写 + 空格分隔」，不要用带下划线的注册名。**

语言文件里的键名、`regname` 都是小写下划线风格，那是给代码看的。
`ename` 是给人看的英文名，照抄键名会被审核判为格式错误。

| ✗ 注册名写法 | ✓ 标题格式 |
|---|---|
| `water_bottle` | `Water Bottle` |
| `multi_tool` | `Multi Tool` |
| `empty_water_canteen` | `Empty Water Canteen` |
| `alfa_zombie_spawn_egg` | `Alfa Zombie Spawn Egg` |
| `litherite_solar_cell` | `Litherite Solar Cell` |

转换代码：

```python
def title_case(slug: str) -> str:
    """water_bottle → Water Bottle"""
    return " ".join(w.capitalize() for w in slug.split("_") if w)
```

**注意 `capitalize()` 不是 `title()`**：`title()` 会把 `it's` 变成 `It'S`，
`capitalize()` 只动首字母、其余转小写，对单个词更安全。

**已经提交过的页面要重建**：`ename` 只在「新增」时有意义，编辑 JSON 里没有这个字段，
所以发现写错时要按新增重走一遍（不要用编辑去改，改不到）。

踩过的坑：Crafting Dead: Survival（4397）第一批 75 条把 `ename` 填成了
`water_bottle` 这种注册名写法，整批重建。

### 6.2.2.9 图标重复不一定是渲染错，先查模组贴图引用

批量渲染后如果发现两个不同物品的图标**字节完全相同**，不要先怀疑渲染器——
先去看模组的模型 JSON，很可能作者自己把贴图路径写错了。

真实案例（Nemo's Carpentry 31737）：`pale_oak_black_stained_glass_door` 的模型
引用了 `dark_oak` 的贴图：

```json
"textures": {
  "bottom": "nemos-carpentry:block/doors/dark_oak/dark_oak_black_stained_glass_door_bottom",
  "lower":  "nemos-carpentry:block/doors/dark_oak/dark_oak_glass_door_bottom_lower"
}
```

游戏内这两个方块的外观确实一样。**照实交付**，不要"修"成不同的图——
那样反而与游戏内不符。

排查脚本（找出贴图引用跨木材的方块）：

```python
import json
from pathlib import Path

A = Path(".../assets/<modid>")
M = A / "models/block"

def model_of(stem):
    bs = A / "blockstates" / f"{stem}.json"
    if not bs.exists():
        return None
    d = json.loads(bs.read_text(encoding="utf-8"))
    v = next(iter(d["variants"].values()))
    m = v["model"] if isinstance(v, dict) else v[0]["model"]
    rel = m.split(":")[-1].replace("block/", "")
    p = M / f"{rel}.json"      # 注意要补 .json
    return p if p.exists() else None

for stem in sorted(b.stem for b in (A / "blockstates").glob("<前缀>_*")):
    mp = model_of(stem)
    if not mp:
        continue
    tex = json.loads(mp.read_text(encoding="utf-8")).get("textures", {})
    wood = stem.split("_")[0]
    if any(f"doors/{w}/" in str(v) for v in tex.values() for w in ["dark_oak", "oak"] if w != wood):
        print(f"{stem} 引用了别的木材贴图")
```

### 6.4 资料页正文：必须写功能（硬约束）

写「物品 / 方块 / 实体 / 状态效果」这类**资料页**的正文，和写模组介绍不是一回事——资料页要回答"这东西有什么用"。

固定顺序：

1. **先查作者写没写过介绍**：Patchouli 手册（§6.3）> `lang/zh_cn.json` 的 `tooltip.*` / `*.desc` / `text.*` > 硬编码在 Java 里的描述（如 `LoreDefinition`）。作者原文可以引用（第 8 条允许作者原话）。
2. **正文必须有「功能」**：是什么、干什么用、怎么获得、有什么效果与限制。
   **只抄游戏内 lore / 剧情文本、不写功能＝不合格**——lore 是氛围，功能才是资料。
3. **作者没写介绍时，读源码把它写出来**：
   - 类继承了什么（`Item` / `ICurioItem` 饰品 / `Block`）→ 决定它能放进哪、怎么用；
   - 注册时给的参数（星级、堆叠上限、耐久）；
   - `canEquip` / `appendHoverText` / 事件里的限制与效果；
   - 有没有 `AttributeModifier` / 药水效果 / `onEquip` 真实加成；
   - 创造标签页 → 获取方式。
4. 拿不准的写「待确认」，绝不编效果（第 18 条）。

**判定"到底有没有效果"的两个 grep**（都不命中＝纯收集/剧情物品，正文据实写"无属性加成"）：

```powershell
# 这个类自己有没有加成
Select-String -Path <Item.java> -Pattern 'AttributeModifier|getAttributeModifiers|onEquip|MobEffect'
# 全仓库有没有按这个 id 实现效果
Get-ChildItem src -Recurse -Filter *.java | Select-String -Pattern '"<item_id>"'
```

写完之后正文至少要有：一句「是什么」＋「功能/效果/限制」＋「怎么获得」，lore 原文可作为引用段落附在后面。
### 6.5 新增资料页（/item/add/）的字段顺序与坑

实测于 `https://www.mcmod.cn/item/add/<classId>/`（**classId 从 URL 现取，脚本里不硬编码**）：

| 顺序 | 字段 | 选择器 | 坑 |
|---|---|---|---|
| 1 | **资料类型**（物品/方块…） | `.common-item-mold-list li a`（选中项带 `data-category-selected='true'`） | **必须先选它**，否则「资料分类」的下拉根本不在 DOM 里 |
| 2 | 资料分类 | `#item-type-select`（bootstrap-select 包的原生 `<select>`）+ `#item-type-custom` | 选「自定义」时把 select 置空 `''`，再把新分类名写进 `#item-type-custom` |

> **硬规则：资料分类必须填，任何资料类型都不例外。** 物品/方块、生物/实体、BUFF/DEBUFF、
> 绑定热键、世界/维度、游戏设定、多方块结构……每一类都有这个字段，**留空 = 页面上显示「未分类」**，
> 审核会打回或至少被降权。批量数据里 `category` 写空字符串时脚本是「跳过不动」而不是「自动填」，
> 所以生成 JSON 时必须显式给出分类名；拿不准就先问用户要分类名，不要留空交付。
> 分类名要和站点上已有的**完全一致**（含全角问号、空格），否则脚本会新建一个近似名，造成同类分裂。

#### 术语与分类：一律以模组自身文案为准

写正文时**所有专有名词取模组自己的说法**（语言文件 `tooltip.*` 与游戏内实际显示），不要用任务书、
子代理报告、或你自己的临时命名。哪怕报告里列了行号证据，只要和模组文案冲突，**以模组文案为准**。

实测例子（乐土终曲刻印体系）：

| 别写成 | 应写成 | 依据 |
|---|---|---|
| 核心增幅 / 扩展核心 | **增幅刻印** | 繁星系 tooltip 原文「每持有一种不同英桀的增幅刻印」 |
| 把挂在核心上的条目叫「核心刻印」 | 见上，叫**增幅刻印** | 「核心刻印」专指 2 个二选一的核心本身，不在 144 条里 |
| 自己起名的分类名 | **站点上已存在的分类名**（含全角问号、空格要完全一致） | 名称不一致会新建近似分类，造成同类分裂 |

**资料分类（`category`）任何资料类型都必须填**：物品/方块、生物/实体、BUFF/DEBUFF、绑定热键、
世界/维度、游戏设定……留空 = 页面「未分类」。批量数据里写空字符串是「跳过不动」而不是「自动填」，
所以生成 JSON 时要么显式给分类名，要么先问用户——**不要留空交付**。

**从子代理的 Markdown 里搬运表格时必须清洗**：反引号 `` ` ``、`**加粗**`、`†`/`※` 之类的
临时标记、以及 `（L1234）` 这种行号备注，都要在转 HTML 时去掉，否则会原样出现在百科正文里。
| 3 | 主要/次要名称、注册名、堆叠、耐久、元数据、附言 | `[data-multi-id="name" / "ename" / "regname" / "maxstack" / "damage" / "metadata" / "remark"]` | 这套 `data-multi-*` 框架**必须用原生 value setter + 派发 `input`/`change`**，直接赋 `.value` 会被忽略 |
| 4 | 小图标 / 大图标 | `#icon-32x-editor`、`#icon-32x`（base64，**不加 `data:` 前缀**，页面自己补）；点「同步至大图标」生成大图 | 不用走文件上传 |
| 5 | 正文 | 勾「源代码编辑器」后是 CodeMirror：`document.querySelector('.CodeMirror').CodeMirror.setValue(html)` | — |
| 6 | 提交 | `#edit-submit-button[data-type=item_add]` → 弹「资料添加确认」→ 再点「确定提交」 | 弹窗分「错误（必须改）/ 警告 / 提示（可忽略）」；**照着错误改就能过**，别绕开 |

**数值字段的坑**：`[data-multi-id="metadata"]`（元数据）、`maxstack`、`damage` 都带 `data-limit-type=int`，**最小值是 1**。给元数据填 `0` 会弹「只能输入 1 到 2147483647 之间的正整数」，提交被卡住。普通物品**不要设置元数据**，留空即可；堆叠/耐久按实际填（≥1）。

**提交确认弹窗里的误报**：它会拦「疑似第一人称/主观的『我们』」和「疑似不规范/错词」——引用作者原文（lore 里有「我们」）时属**误报，可忽略**，点「确定提交」照常通过。

两个容易被当成"坏了"的现象：

- 一开始 `#item-type-select` 查不到，不是页面没加载，而是**资料类型还没选**；
- 提交弹窗只是「1 处提示（可以忽略）」时也算通过，点「确定提交」即可。

排序与附言：正文里必须写功能（§6.4），获取方式写不出来的如实写"仅创造模式可获取 / 生存获取途径待确认"——站点自己的提示也认可这种写法。
### 哪些类型天然没有图标

| 资料类型 | 图标 |
|---|---|
| 物品 / 方块 | 有（方块必须立体）|
| 生物 / 实体 | **无**（UV 贴图不是图标，留空 + 勾删除）|
| 游戏设定 | **无** |
| 自然生成 | **无** |
| 绑定热键 | **无** |
| 世界 / 维度 | 一般无 |
| BUFF / DEBUFF | 取决于有没有独立图标 |

**例外**：刷怪蛋是物品，但有图标——它的两色蛋形可以由实体注册的
primaryColor / secondaryColor 渲染出来（见 `scripts/render-spawn-egg.py`），
不要因为「实体没图标」就把刷怪蛋也留空。

#### 清空正文要显式给空字符串（脚本 v2.38 起）

再编辑退回项时经常要「把正文清空」，比如审核说「正文重复率太高，需要留空」。

**脚本在 v2.37 及之前用 `if (it.html)` 判断**，空字符串是 falsy，直接跳过 ——
结果是不但没清空，反而原正文原样保留，白跑一次提交。

v2.38 起改成 `if (it.html !== undefined)`：**字段存在就写，空字符串表示显式清空**。

所以数据里要这样写：

```json
{ "verifyId": 817565, "html": "", ... }     ← 清空正文
{ "verifyId": 817565, ... }                 ← 不碰正文（字段省略）
```

区别在于**有没有 `html` 这个键**，不在于它的值真假。

UEditor 空内容时还会残留一个占位段落，脚本里补了一次 `ed.setContent('')` 兜底。

#### 同类物品只写一条正文，其余留空并请求创建抽象

批量新建同类物品时（一批化学品、一批炸药、一批刷怪蛋），**不要把同一段模板正文复制到每一条**。

原因：审核的判定标准里有「正文重复率」。二三十条几乎一样的说明会被判重复率过高直接退回，
真实退回原话是：

> 正文重复率太高，需要留空，通过后协助创建抽象

mcmod 的「抽象」是一个通用介绍页，多个资料页可以引用它。同类条目共用一个抽象页，
既避免重复，改一次就全更新。

### 6.7 资料页正文的排版细则（实测于 UEditor）

**单句过长必须拆行。** 一个 `<p>` 只放一句（或一个完整语义单元）；一句话里堆了三四个分句、逗号套逗号，读者一眼扫不完。表格单元格里尤其要拆：

```html
<!-- 反例：一个 <p> 里塞了复活规则 + 侵蚀代价 -->
<td valign="top"><p>将 5×5 范围内所有生物生命值恢复至满；范围内若有对应生物的掉落物或头颅，可将其复活（消耗一件媒介，同一死者仅能复活一次）。释放后自身崩坏能侵蚀增加 50%。</p></td>

<!-- 正例：按语义拆成两段 -->
<td valign="top">
  <p>将 5×5 范围内所有生物生命值恢复至满；</p>
  <p>范围内若有对应生物的掉落物或头颅，可将其复活（消耗一件媒介，同一死者仅能复活一次）。释放后自身崩坏能侵蚀增加 50%。</p>
</td>
```

**短资料页用加粗段落，长资料页必须用 `[hN=]`：**

**短资料页（物品/方块）不用 `[hN]`**，直接加粗段落即可：

```html
<p><strong>黑渊形态</strong></p>
```

**什么时候必须用 `[hN=]` 标题（补充规则）**

- **物品/方块等短资料页**：正文只有一两段，不需要标题，用加粗段落即可（上一条规则）。
- **长篇资料页必须建目录**：游戏设定、体系总览、逐条明细表这类内容（正文超过约 3000 字符，或含多个独立章节／十几张表）**一定要用 `[h2=]`、`[h3=]` 分层**，否则页面没有目录、读者无法跳转，审核也会认为结构不清。
- 层级用法：`[h2=章节名]` 做一级分区（如「概述」「核心二选一」「十二分类总览」「分类明细」），`[h3=分类名]` 做二级分区（如空梦、浮生、繁星…）。
- 标题单独占一个 `<p>`：`<p>[h2=概述]</p>`；不要和正文写在同一个 `<p>` 里，也不要手写数字编号（百科会自动编号）。
- 判断标准一句话：**读者需要靠目录跳转，就必须有 `[hN]`；一段话读完，就不需要。**


**模组「简介」不是操作手册。** 主页面的模组介绍要回答「这是什么、玩起来什么感觉、有什么内容」，
不是给出规则清单。判断方法：

| 该写进简介 | 该写进资料页 / 游戏设定 |
|---|---|
| 世界观引入、维度氛围、玩家会经历什么 | 具体数值、价格表、键位表、分类明细 |
| 核心玩法循环（刻印 → 组合 → 试炼） | 每一条刻印/物品的逐行说明 |
| 装备的性格（「黑渊削上限，白花治队友」） | 「第零额定功率消耗 150 能量、冷却 5 分钟」 |

写法：第二人称、短段落、每段一个意思；**表格最多 1~2 张，能删就删**；
出现「价格 3000 / 升级消耗 10 级经验 / 键位 R C V」这类内容就该挪到资料页。
反例：把简介写成 5 张价格表 + 键位表 + 规则列表 = 手册。



#### 注册名（regname）与原名（ename）都是必填项

**踩过的坑（两次）**：

1. BUFF/DEBUFF 那批 22 条全部被退回，理由「没有注册名」——当时以为效果没有物品 id，
   其实效果同样有注册表 id。
2. 自然生成那批 8 条被退回，理由「需要补充注册名/原名」——结构同样有注册表 id，
   当时整批 `regname` 与 `ename` 都留空了。

#### regname 填什么

| 资料类型 | 注册名填什么 | 例 |
|---|---|---|
| 物品 / 方块 | 物品注册表 id | `lastsongofelysian:core_of_fire` |
| BUFF / DEBUFF | 效果注册表 id | `lastsongofelysian:red_ink` |
| 生物 / 实体 | 实体类型 id | `lastsongofelysian:elysian_hero_npc` |
| 世界 / 维度 | 维度 id | `lastsongofelysian:elysian_realm` |
| **自然生成 / 结构** | **结构 id**（`data/<ns>/worldgen/structure/*.json` 的文件名）| `minecraft:village_plains` |
| 绑定热键 | **留空**（本地化 key 不是注册名）| — |

**自然生成页的注册名从哪找**：

```
data/<namespace>/worldgen/structure/<结构名>.json   → regname = namespace:结构名
```

只有结构定义文件才算。以下两类不是结构，别硬填成结构 id：

- 模组只替换了模板（如掠夺者前哨站的 25 个 nbt），结构本身还是原版的 → 填原版 id
- 模板池（`data/<ns>/worldgen/template_pool/...`）→ 填模板池路径，如 `minecraft:village/common`

#### ename 填什么

| name 是什么语言 | ename |
|---|---|
| **中文**（模组有 zh_cn） | **必填英文名** |
| **英文**（模组无中文，name 本身就是英文） | 可留空 |

**关键**：`name` 是中文时 `ename` 不能空——这正是 15261 被退回的直接原因：
八条页面的 name 都是「平原村庄」这类中文，ename 全空，审核要的就是那一列英文原名。

原版结构没有自定义英文名时，用结构 id 转标题格式并在括号里注明变体：

```
minecraft:village_plains   → Village (Plains)
minecraft:village_desert   → Village (Desert)
minecraft:pillager_outpost → Pillager Outpost
```

#### 唯一例外：抽象资料与通用文本

这两类是**虚拟资料**，游戏里不存在，所以 `regname` 与图标都必须留空（见 §6.1.11）。
除此之外的每一条真实资料，两个字段都要有值。

#### 自检

```python
# regname 为空 → 必退
[r["name"] for r in data if not r.get("regname")]
```

**要求**：

- 一律用 **ASCII**（别把中文写进 regname，如 `signet_空梦` 是错的，应 `signet_reverie`）；

#### 清点完整性：方块（BlockItem）极易被整批漏掉

**踩过的坑**：图标生成脚本只扫 `assets/<ns>/textures/item/`，于是 98 条物品全齐，
**但模组的 2 个方块（魂钢块、往世乐土入口）一条都没进清单**——因为方块的贴图在
`textures/block/`，注册也在独立的 Block registry 里。审核侧看到的「物品/方块」自然就少了这两块。

**方块的可靠清点方法**（任取其一或交叉验证）：

| 方法 | 位置 |
|---|---|
| blockstates | `assets/<ns>/blockstates/*.json`，**一个方块一个文件**，最准 |
| 方块模型 | `assets/<ns>/models/block/*.json` |
| 注册表 | `registry/ModBlock*.java`、`DeferredRegister<Block>`、`BLOCKS.register("...")` |
| 物品形态 | 方块自带 BlockItem 时也会出现在物品注册表里，但**图标要从 block 贴图取** |

**交付前必须做一次对账**，差额逐条解释：

```
物品清单条数  vs  物品注册表实际条数
方块清单条数  vs  blockstates 文件数
```

对不上的常见原因（都要在清单里补上或明确写“不收录 + 理由”）：

- 方块（BlockItem）：贴图在 `textures/block/`，不在 `textures/item/`；
- 刷怪蛋：图标由两色程序化生成，没有静态 png；
- 3D 模型物品（Blockbench）：贴图是 UV 图集，不能当平面图标用；
- 只有语言文件、没有贴图的纯逻辑物品；
- 有贴图但没注册的残留素材（应排除，并说明理由）。

**方块资料的字段**和物品一致（`type` 仍是 `物品/方块`），但正文要写清：怎么获得（合成表）、
方块属性（硬度/抗爆/挖掘等级/是否受重力/发光等级）、以及它的功能。



#### 没有图标时：必须清空大图标并勾选「删除大图标」

**踩过的坑**：生物/实体那批没带图标，被退回的理由是「勾一下删除大小图标，里面是空的」。
即：大图标字段是空的、但页面上仍保留了该栏，审核判为空值错误——**空不是「没有」，要显式删除**。

规则：
- 任何资料只要**不上传图标**，就同时做两件事：清空「大图标」栏 + 勾选「删除大图标 / 删除大小图标」；
- 只清空不勾选，仍会被退回；
- 批量脚本 v2.5 起已自动处理：`icon32` 为空时会去找文字含「删除大图标/删除大小图标」的
  复选框并点击（`mcmod-batch.user.js` 的 `fillOne`）。
- 有图标时则相反：大小图标都要填，或小图标填完点「同步至大图标」。


### 图标规范（审核实测要求）

**1. 放大一律用「临近（保留硬边缘）」= NEAREST，不要平滑插值。**

审核原话：「放大时选『临近（保留硬边缘）』就不会模糊了」。用 LANCZOS/BICUBIC 放大会产生大量过渡色，
提交后会被判「图标模糊」退回。判定方法：看图片颜色数——18×18 原图放大到 128×128 后，
NEAREST 的颜色数等于原图（个位数到几十），LANCZOS 会有上千种颜色。

正确写法（Pillow）：

```python
def _fit(im, size):
    '''放大用 NEAREST（保留硬边缘），缩小用 LANCZOS。'''
    if im.width < size:
        return im.resize((size, size), Image.NEAREST)
    return im.resize((size, size), Image.LANCZOS)
```

注意：**缩小时用 LANCZOS 是对的**（缩小平滑避免锯齿），只有放大才必须 NEAREST。

**2. 方块类资料必须交「立体图标」，单面贴图会被退回。**

审核原话：「需要上传立体图标，提交的是单面纹理」。方块在游戏里显示的是等轴测立方体，
只交 `textures/block/*.png` 的平面图不算。

用 `scripts/render-block-iso.py`（见 §5.5）：取 top/side 贴图，按顶面 1.0 / 左面 0.8 / 右面 0.6
的明暗铺到等轴测三面上，512 超采样后缩到 128/32。

**比例是这一步最容易错的**：侧面高必须等于顶面半宽（`sh = w`），写成 `0.75w` 会让
总高只有总宽的 87.5%，图标看着扁。渲染完先打开 `-128.png` 预览图目视确认一遍再交付。

**3. 大图标为空时必须勾「删除大图标」，否则判空值错误。**

审核原话：「勾一下删除大小图标，里面是空的」。空不是「没有」，要显式删除。

> **反过来同样成立：有图标时必须确保「删除」不被勾选。** 这两个勾选框是页面的残留状态——
> 同一页面先跑过一批 `icon32` 为空的数据，框会保持选中；接着跑带图标的数据时，如果不主动取消，
> 提交会把刚写入的图标一起删掉。批量脚本 v2.7 起在 `icon32` 有值时会先取消这两个勾选。
>
> **关键：mcmod 会自动同步大小图标，所以「有任意一张图」就等于两个都有，两个框都不能勾。**
>
> 只给 `icon32`、不给 `icon128` 是常态（大图标一般用不着）。上传小图标后站方会自动同步出大图标，
> 这时如果按「小图标有值→取消删除、大图标没值→勾选删除」分开处理，反而会把大图标判成空值，
> 触发「大图标为空」的审核错误。**不要分开处理。**
>
> 判定口诀：**有 icon32 或 icon128 任一 → 两个都取消勾选；两个都没有 → 两个都勾选**。
>
> v2.37 起脚本按这条实现，并在日志里打印
> 「有图标，已取消「删除图标」勾选 N 个（大小图标自动同步）」或
> 「无图标，已勾选「删除图标」N 个」。
>
> 已经提交、图标被误删的条目，可以按 §6.6 的「审核中条目修正」用 `verifyId` 重新提交。

**4. BUFF/DEBUFF、实体的效果图标也要给，不能用原版 missing texture 蒙混。**

原版 `missing_no.png` 只在**模组确实没有该贴图**时用，并在附言里说明原因。

#### 缺图标时用原版 missing texture 占位

**先区分「模组缺图 bug」和「真的没有图标」**：

- 如果条目有注册 id、按命名规范应该能找到 `textures/<类别>/<id>.png`，但文件**缺失** →
  这是**模组 bug**，不是资料问题。正确做法是**补资源文件**（照同族已有图标的先例复制，
  例如所有刻印类 buff 都用 `textures/item/signet_of_<英桀>.png` 复制一份到 `textures/mob_effect/`），
  然后告诉作者；**不要用占位图糊过去**。
- 只有在资源形态上根本不存在图标时（程序化绘制、3D 模型 UV 图集），才谈占位。

占位规则：资源里确实没有图标的条目（例如 `textures/mob_effect/` 下缺失的 buff），**不要留空、也不要自己画图案**，
统一用原版缺省材质——**品红(#F800F8)与黑的棋盘格**（材质包出错时游戏里显示的那张）当占位：

```python
# 16×16，8px 棋盘，再 NEAREST 放大到 32/128
img = Image.new("RGBA", (16, 16), (0, 0, 0, 255))
for y in range(16):
    for x in range(16):
        if ((x // 8) + (y // 8)) % 2 == 0:
            img.putpixel((x, y), (248, 0, 248, 255))
img.resize((32, 32), Image.NEAREST)   # 小图标
img.resize((128, 128), Image.NEAREST) # 大图标
```

要点：
- **必须 NEAREST**（不能用 LANCZOS），否则边缘糊掉，看不出是占位图；
- 占位图标要**在备注/正文里说明**是缺省材质，不要让读者以为是正常的 buff 图标；
- 一旦资源里补上了真图标（比如作者后续更新），重新生成即可覆盖——脚本里把「找 png」放在前面、
  「用 missing」放在兜底分支，就自动优先真图。

#### 交付格式：HTML + Markdown 双交付（默认）

写完资料页不要再只给 JSON 或只贴一段 HTML 到聊天里。**默认交付三份文件**：

| 文件 | 用途 |
|---|---|
| `<名字>-片段.html` | 直接粘进百科「源代码编辑器」的那一段（含 `[hN=]` 标题） |
| `<名字>.html` | 完整 HTML 文档，双击能在浏览器预览（`[hN]` 已转成真 `<h2>`/`<h3>`，带内建表格样式） |
| `<名字>.md` | Markdown 版，便于阅读、diff 与二次编辑 |

原因：用户会把 HTML 贴回来做修改，说明**成品就是 HTML**；只给 JSON 等于把渲染工作丢回给用户。
JSON 仍然保留，但它是「批量提交的输入」，不是交付物。

导出脚本：`E:\Mod\百科-乐土终曲\export_docs.py`（`export(name, fragment, title)` 直接出三份）。

搬运前必做的清洗（脚本里已内置，手写时也要做）：
- `，。`、`；。` 这类标点残留 → 合成一个句号；
- 反引号、`**`、`†`、`※`、`（L1234）` 等 Markdown/行号痕迹；
- 表格单元格里超过约 34 字的句子，按语义拆成多个 `<p>`（§6.7）。

**长篇资料必须带 `[h2=]`/`[h3=]` 目录**（见上一条），交付前用
`grep '\[h[0-9]=' 文件` 自查标题是否齐全、层级是否合理。


**列表**（class 不必手写，见下）：

```html
<ul class="list-paddingleft-2">
  <li><p>普通攻击扣除目标生命值上限，扣除量不可治愈。</p></li>
</ul>
```

**表格**：第一行用 `<th>`（这个必须手写），其余单元格 `<td valign="top">`，单元格内容用 `<p>` 包住。
**不要用单列表格。** 只有一列、下面挂 N 行的表最浪费版面（12 个名字占 12 行），
读者视线被拉长，页面还显得空。判断标准：

| 内容 | 怎么写 |
|---|---|
| 一串并列的短名词（12 枚核心、6 种材料名、若干标签） | **行内顿号**：`<p>分别是：理、空、雷……侵蚀。</p>` |
| 需要逐条说明的条目（每条都有对应的数值/效果） | **≥2 列的表格**（名称在左，说明在右） |
| 有层级或分类的清单 | `<ul>` 列表，每项一个 `<p>` |

一律避免：`<table>` 里只有一个 `<th>`、每行只有一个 `<td>` 的写法。


**粘贴进「源代码编辑器」后，编辑器会自动规范化 —— 这是正常的，别改回去**：

| 你写的 | 编辑器变成 | 说明 |
|---|---|---|
| `<ul class="list-paddingleft-2">` | `<ul class=" list-paddingleft-2">`（多一个空格） | UEditor 自己加这个 class，**手写不写都行** |
| 没有 `<tbody>` | 自动补 `<tbody>` | 正常 |
| `<tr><th>…` | `<tr class="firstRow"><th>…` | **表头行**被标记 firstRow 是对的（§2.2 禁的是「用 `<td class="firstRow">` 冒充表头」） |
| 长文本单元格 | 自动加 `style="word-break: break-all;"` | 正常 |

**核对方式**：粘贴后切到「正文预览」看实际渲染，别盯源码——源码里的 class/tbody/firstRow 是编辑器加的，判断合规看预览效果与 `[hN]`/表格结构即可。
### 6.7.1 图标优先给 128：有图标就必须带 `icon128`

**从 12157（De-Extinction）起，所有新增资料只要给了 `icon32`，就必须同时给 `icon128`。**

只给 32、让站方「同步至大图标」把 32 放大到 128，等于让读图的人看一张放大糊掉的图；
模型渲染类的图标（机器、家具、复杂方块）尤其明显——32 像素根本装不下结构细节。

```json
{
  "name": "DNA Extractor",
  "icon32":  "…",   // 32×32
  "icon128": "…"    // 128×128，必须给
}
```

| 来源 | icon32 | icon128 |
|---|---|---|
| 16×16 原图（普通物品） | 16→32 **NEAREST** | 16→128 **NEAREST** |
| 128×128 原图（高清物品） | 128→32 **LANCZOS** | 直接用原图 |
| 模型渲染（`render-mc-model.py`） | 512→32 一次缩放 | **512→128 一次缩放** |

**关键：icon128 不要从 icon32 再放大。** 那会二次损失。两者都应该从原始图/渲染结果各自缩出。

批量脚本 v2.39 支持 `icon128` 字段，会独立上传大图标，不走「同步至大图标」。

**自查**：

```python
miss = [r["name"] for r in rows if r.get("icon32") and not r.get("icon128")]
assert not miss, f"缺 icon128: {miss}"
```

> 历史批次（rex / mse / gte / cds 等）只给了 icon32，不回头补；从 12157 起执行这条。

### 6.8 图标：从哪来、多大、什么时候拿不到

**不要假设贴图是 16×16。** 实测本模组 98 个物品里 86 个是 **128×128**，另有 256/512/64/16 不等——按 16×16 用最近邻"放大"到 32，等于把高清图压成马赛克（踩过）。

**正确取图流程**：

1. 读 `models/item/<id>.json`，从 `textures.layer0`（或 `"0"`、`particle`）拿到**真实贴图路径**，不要按 `<id>.png` 猜文件名；
2. 同一个贴图可能被多个物品共用（例如各刻印的「增幅/核心」子物品全都用 `item/signet_xxx`），这是**正常**的，不是错位；
3. 小图标 32×32：用 **LANCZOS** 从原图降采样（等价于游戏把 HD 贴图渲染到 32 像素）；
4. 大图标直接上传 **128×128** 原图，**不要**用页面「同步至大图标」把 32 放大（二次损失）。扩展 v2.2+ 支持数据里带 `icon128` 时独立上传。

**拿不到图标的情况（必须排除，不能硬凑）**：

- 模型里有 `"elements"`（Blockbench 自定义 3D 模型，如弓）→ 那张图是 **UV 贴图集**，直接当图标就是一团花纹。这类物品**必须真渲染或让作者给图**，不要提交。
- 贴图文件不存在 / 物品根本没在注册表里（遗留贴图，如 `image_19`）→ **不收录**，别为了凑数提交。

自查命令（Python + Pillow）：

```python
d = json.loads((models / f"{item_id}.json").read_text(encoding="utf-8"))
layer = (d.get("textures") or {}).get("layer0", "")     # 真实贴图
custom3d = "elements" in d                              # 需要真渲染
```
