## ⚠️ 红线：模组页只写摘要，细节归资料页

审核原话（已退过至少三次）：

> （部分含有）**对单个资料过于详细的介绍需要写到对应的物品里，模组正文仅需摘要**

这条是模组页最容易踩的一条，而且**结构全对也照样退**。

### 该下沉的特征

一段话里出现下面任一特征，就该搬到对应资料页：

| 特征 | 例子 |
|---|---|
| 只讲某一个物品/方块的产出、耐久、概率 | 三档战利品箱分别拆出 1、3、6 片…牛头人之锤拆 8 片 |
| 只讲某一个实体的特殊机制或触发条件 | 女鬼要身边摆 8 朵凋零玫瑰、玩家自身带上凋零效果 |
| 只讲某一条状态效果的获得方式 | 蚂蚁信息素由收服后的工兵蚁定期赋予主人 |
| 数字很多但都是同一个对象的参数 | 血量分 8 档逐档锁定 |

### 该留在模组页的

| 内容 | 为什么留 |
|---|---|
| 多个对象的分类概览 | 「分三类」「共 23 种」——这是模组级结构 |
| 全族共用的机制 | 好感度、经验等级、饰品栏、交易体系 |
| 前置、兼容、配置项 | 影响能不能跑，属于模组层面 |
| 一句话定位 | 「本模组是 X 的 Y 扩展」 |

### 检验问句（交付前必答）

> 把这段单独抽出来，贴到那个物品/实体自己的页面上，读者会觉得错位吗？

**不觉得错位 → 它本来就是资料页的内容。**

### 判据：数一下主体数

```
一段话里出现的「被描述对象」有几个？
  ≥2 个  → 这是模组级概览，留在模组页
  =1 个  → 这是资料页的内容，下沉
```

### 具体改法

| 反例（写在模组页） | 改成 |
|---|---|
| 「三档战利品箱分别拆出 1、3、6 片，普通武器 2 片…」整段产出表 | 一句概括「产出量按战利品档次递增，从低档的 1 片到半身像的 12 片」，明细进砂轮物品页 |
| 23 种生物的收服条件逐条写 | 一张三行的表（额外条件类型 / 涉及生物 / 要做什么）+ 两个特例，明细进各实体页 |

### 资料页还没建怎么办

允许先在模组页承接，但必须：

1. **表格化**（散文式的逐条列举最容易被判「碎」）
2. 交付说明里注明「这些数值待拆到 XX 资料页」
3. 尽快把资料页建起来，之后回删

### 真实案例（2026-11-13）

一台 AI 读完拆分后的 skill 交付了怪物娘模组介绍：结构完全合规，
但把砂轮的六档产出片数、23 种生物的收服条件全写进了模组页 —— 仍会被退。
**原因不是模型不听话，是这条规则当时不在 skill 里。**
审核附言里出现过的规则，必须当天进规则块。

## 6 风格基线

- 数字与单位之间加半角空格：`提高 20%`、`冷却 1 秒`、`3×3`。
- 多项数值用顿号分隔并各自带空格：`情绪 +4、亲近 +3、怨恨 −1、忠诚 +1`（减号用 `−` U+2212）。
- 条件统一 `≥ ≤ > <`，不混用全角 `＞`。
- **数字或罗马数字后面不放全角标点**，用半角 `. ` + 空格：`Ⅰ. 五维总览`、`1. 亲近`。
- 每句句号收尾（纯名词格可例外）。
- **作者的措辞不要改**：只做标点、空格、句末标点、`注：`/`注意：` 前缀（第 24 条）、反引号误用这类整理。专有名词和 mod 自造术语一律原样保留。
- **默认全篇不上色**（第 26 条禁过于鲜艳/五颜六色的文字颜色）。
- **第一次接手某个页面时，告知一次**（只说一次，别反复推销）：

  > 百科支持给文字上色，需要的话你直接告诉我「哪句话、什么颜色」，我来加；不说我就一律不上色。

- **只由用户发起、并由用户指定范围与颜色**：用户没点名的那段文字，一个字都不许加色；不要"为了好看""为了强调"自作主张。
- 上色写法（示例代码）：

  ```html
  <span style="color: rgb(255, 0, 0);">要上色的文字</span>
  ```

  `rgb(r, g, b)` 逗号后有空格、`;` 写在引号内。
- 用户指定的颜色照办；但如果明显踩第 26 条（纯红/纯白/荧光色、五颜六色），提醒一句他可能被退，再问是否换成低饱和的。
- 未实机验证的结论不要写成事实（第 18 条）。


### 6.1 别把介绍写成清单填空（"小学生感"）

最常见的烂法：**一长串名词 + 一句抽象总结**。具体名词本来是好事，但被那句总结一冲，读者什么都没记住。

反例：

> 装备方面有天火大剑、伊甸之星、凤凰下、深渊之花、画笔与往昔低语等，各自带有独立的技能或效果。

问题不在文笔，在**结构**：

- "有……等"是填空壳，六个名词排排坐，读者只知道"有这些东西"；
- "各自带有独立的技能或效果"是废话——任何装备都有技能或效果；
- 六个具体名词（好东西）被一句抽象总结（把具体感冲掉）。

正例（同一页里就该这样写）：

> 乐土中的材料分几档：魂钢有锭、粒、块三种形态；崩坏能抑制器分低、中、高三级；生物残渣可以逐级压缩两次。

为什么正例成立：它给的是**结构信息**（三形态、三级、压缩两次），读者能想象出层级关系。

**改法三选一（按投入排）**：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A 给每件一个身份标签** | 至少让读者感到"这些是有分工的"：`天火大剑是重型武器，伊甸之星偏向范围控制，往昔低语与刻印构筑联动` | 每件都想提一句时 |
| **B 按功能分组**（推荐） | 不列名字，改列**类别**：`装备分三类：A、B 是主战武器；C、D 偏向场控；E 是可切换模式的工具` | 条目多、且能归类时 |
| **C 砍掉总结句** | `装备方面有 A、B、C、D、E、F 等，各有独立技能` | 实在不想展开时的底线 |

**推荐 B**：和"魂钢三形态"那种写法同源（给结构不给名单），整节风格统一，还不需要给每件都写介绍。

**判断口诀**：读完那句，读者能不能说出"这些东西之间有什么差异"？说不出，就是清单填空。

**适用范围**：不止装备栏。材料、生物、刻印、界面功能，任何"一组同类东西"的列举都适用。
### 6.2.2 食物属性统一叫「饥饿值」，不叫「饱食度」

写食物资料页正文时，回复量一律写作 **饥饿值**，不是「饱食度」。

```
✅ 回复 6 点饥饿值、4.8 点饱和度
❌ 回复 6 点饱食度、4.8 点饱和度
```

`饱和度` 保留（这是 Minecraft 的独立属性，与饥饿值并列）。

### 6.2.2.1 每个模组都要写模组页介绍（默认项）

拿到一个模组要建资料页时，**默认同时产出模组页正文**，不需要用户单独提。

资料页（物品/方块/实体）讲的是单个条目，模组页讲的是整体：这模组是干什么的、加了哪些东西、怎么玩、有什么前置。少了它，一批资料页就成了没有目录的散页。

写模组页用的数据通常和资料页是同一批（jar 里的 lang、配方、注册代码），所以一起做不额外花多少时间；分开做反而要重新翻一遍。

**交付时的默认清单**：

```
<模组>-介绍-<classId>.html      模组页正文
<模组>-物品导入-<classId>.json  物品页
<模组>-实体导入-<classId>.json  实体页（有实体时）
<模组>-方块导入-<classId>.json  方块页（有方块时）
<模组>-编辑-<classId>.json      已有页面补正文时
```

### 6.2.2.3 模组页不写「版本信息」节

模组页正文**不要**单独写「版本信息」「版本号」「作者与协议」这类小节。

原因：mcmod 的模组页有自己的版本、作者、协议字段，编辑后台单独维护，正文里再写一遍就是重复录入，而且版本一更新正文就过期。

页面上真正需要写的是**模组做了什么**，不是它是什么版本。

**这条是硬禁止，不是建议。** 常见违规形态：

| 违规写法 | 正确做法 |
|---|---|
| `[h1=版本]` 或 `[h1=版本信息]` 独立成节 | 整节删掉 |
| 末尾加一句「版本 1.0.0，作者 XXX」 | 作者不写；版本差异并进正文对应段落 |
| `[h1=作者]` / `[h1=致谢]` | 删掉，致谢进附言 |
| `[h1=前置]` 里写版本号 | 只写「需要 XX 模组」，不写具体版本号 |

不写：

```
[h1=版本信息]
当前版本 1.0.2，对应 Minecraft 1.18.x，基于 Fabric。
作者 Reparer，协议 CC0-1.0
```

该写的版本相关内容放进正文本体里：

- 依赖关系写成「前置」一节（这些影响能不能跑）
- 特定版本的机制差异直接写进对应段落（「1.20.1 之后改成 NeoForge」）
- 作者、协议、源码链接都不写

### 6.2.2.31 长介绍用 `[h2=]` 分节，不要一律禁用标题

**介绍够长时，让页面目录显示出来，比压成一大坨更好读。**

| 情况 | 标题栏 | 分节 |
|---|---|---|
| 短介绍（一两段就说完）| `[ban:title_menu]` 禁用，省得目录只有一项 | 不需要 |
| **长介绍（有多个主题）** | **不禁用**，让目录出现 | **用 `[h2=]`** 分节 |

原文的 `[h1=概述]` / `[h1=画廊]` 保留不动，**自己补充的内容用 `[h2=]`**，
不要新增 `[h1=]`——h1 是原文的层级，另起 h1 会和「概述」「画廊」并列，结构上不对。

**⚠️ 这条只适用于「模组页」，资料页不适用。**

模组页上已经有原文的 `[h1=概述]` / `[h1=画廊]` 作父级，所以自己补充的用 `[h2=]` 是对的。
**资料页（物品/方块、生物/实体、游戏设定、自然生成……）没有原文 h1**，
标题必须从 `[h1=]` 起——用 `[h2=]` 会被判「文中有跨级标题」：

```
✗ 资料页直接用 h2
  <p>[h2=战利品方块与对应的表]</p>     ← 前面没有 h1，跨级

✓ 资料页从 h1 起
  <p>[h1=战利品方块与对应的表]</p>
```

判断口诀：**看这个页面本身有没有原文的 `[h1=]`**。

⚠️ **这条对模组页也适用**。有些模组的原介绍只给了图片和一段文字，**一个标题都没有**
（例：Exline's Awnings 28508 的原文就是 `<p><img>文字</p>` + 一个图片表格）。
这时候加 `[h2=内容]` 一样会跨级——必须用 `[h1=内容]`，或者干脆不加标题。

三种情况的实际处理：

| 原文标题情况 | 自己补充时用 | 例子 |
|---|---|---|
| 有 `[h1=概述]` / `[h1=画廊]` | `[h2=]` | Simple Wooden Pipes 15375、Factory Blocks 20843 |
| **没有任何标题** | `[h1=]`，或者不加标题 | Exline's Awnings 28508 |
| 资料页（天生无 h1） | `[h1=]` | Crafting Dead 战利品表 |

**提交前跑检查器**：

```powershell
python E:\Mod\模板与工具\发布\mcmod-page\scripts\check-page-structure.py 草稿.html
```

它检查五项：跨级标题、HTML `<h2>` 误用、百科不支持的标签、标签闭合平衡、
`[ban:title_menu]` 与标题的搭配。


有（模组页、教程页）→ 用 h2；没有（资料页）→ 从 h1 起。

实例（Simple Wooden Pipes 15375）：

```html
<p>[h1=概述]</p>
<p>本模组添加了一些廉价且遵循原版风格的木制管道和泵。</p>

<p>[h1=画廊]</p>
<table>…两张图…</table>

<p>[h2=内容]</p>
<p>[h2=管道]</p>
<p>[h2=泵]</p>
<p>[h2=温度限制]</p>
<p>[h2=配置]</p>
<p>[h2=前置]</p>
```

结尾**不写** `[ban:title_menu]`，目录会列出全部 h1/h2。

### 6.2.2.31.1 「短介绍」到底多短：给个量化线

§6.2.2.31 只说「短介绍禁用标题」，没说多短算短。实测补三条线：

```
字数 < 600                    → 加 [ban:title_menu]（唯一条件，不看标题数）
600 ≤ 字数 < 900 且 标题 ≤ 3   → 也可以加（目录两三行同样没导航价值）
其余                          → 不加，让目录显示
```

**为什么字数优先**：目录的作用是「跳着查」。几百字的页面读者一屏扫完，
4 个标题的目录也就 4 行，纯占位。

⚠️ **不要把「标题数」当必要条件**。曾经写成「字数 < 600 **且** 标题 ≤ 3」，
结果 373 字、4 个 h2 的页面被判成不该 ban —— 字数才是主因。

#### 实例对照

| 页面 | 字数 | 标题 | ban | 依据 |
|---|---|---|---|---|
| RGB 染色桶（新例） | **373** | 1+3 | **加** | 字数 < 600，**4 个标题也照样加** |
| Canned Food and Drinks | 499 | 1+1 | **加** | 字数 < 600 |
| Self Damage Knife | 388 | 1+2 | **加** | 字数 < 600 |
| CtE Custom Uniques | 696 | 1+2 | **加** | 600~900 且标题 ≤ 3 |
| Simple Wooden Pipes | 704 | 2+6 | 不加 | 标题 8 个，目录有价值 |
| Factory Blocks | 670 | 2+5 | 不加 | 标题 7 个 |
| Universal Electricity | 1036 | 1+3 | 不加 | 字数 > 900 |

#### 加在哪

```html
<p>[ban:title_menu]</p>      ← 独占一个 <p>，放正文最前
<p>[h1=概述]</p>
```

**不是删标题**——标题还留着分节，只是关掉右侧目录。两件事分开：
删标题解决「h1 太多」，加 ban 解决「标题少但不需要目录」。

### 6.2.2.32 贴原文 HTML：图和链接不能丢，其余格式可以简化

**保真的底线是「图能显示、链接能点」，不是「一个标签都不许动」。**

| 必须保留 | 可以简化 |
|---|---|
| `<img src="…">`（连同 `width` / `height` / `title` / `alt`）| `<span style="text-wrap-mode: nowrap;"></span>` 这类空壳 |
| `<a href="…">` 及其文字 | 冗余的嵌套 `<p>` / `<strong>` |
| 原文的 `[h1=]` 标题文字 | `_src` 属性（编辑器会自己补）|
| 原文段落文字 | 表格的 `width` / `style` 细节 |

实测：原文表格里的 `style="word-break: break-all;"`、`_src` 属性都可以不要，
图片照样正常显示；但 `src` / `width` / `height` / `title` / `alt` 缺了会显示异常。

### 6.2.2.32.1 原文内容要归到 `[h1=概述]` 下，不能散在标题外面

「不必原样保留原文」说的是**可以删减冗余格式**，不是「原文可以飘在最前面」。

```
✗ 错：原文段落和图片顶在最前，后面才起标题
  <p>这个模组为 灵灾 添加了一些饰品…</p>
  <p>两张图</p>
  <p>[h1=内容]</p>
  <p>共十九件饰品…</p>

✓ 对：先起概述，原文全部放进这一节
  <p>[h1=概述]</p>
  <p>这个模组为 灵灾 添加了一些饰品…</p>
  <p>两张图</p>
  <p>共十九件饰品…</p>
  <p>[h1=分类]</p>
```

判据很简单：**页面上任何一段内容都必须落在某个标题下面**。
第一段内容之前，必须先有 `[h1=]`。原文没有标题的就自己起一个「概述」。

### 6.2.2.33 标题要按「读者会不会跳着找」分，不要一节一个 h1

长介绍用 `[h1=]` 分节是对的，但**不是每一节都值得占一个目录项**。

#### 判据

| 这一节 | 配标题吗 | 理由 |
|---|---|---|
| 读者会主动跳过去找（分类、获取方式、数值表）| **配 `[h1=]`** | 目录要能直达 |
| 正文顺序读的说明段（机制解释、原理）| 看长度：≥150 字配 h1，否则加粗 | 短了跳过去只有两行，反而别扭 |
| 一句话的尾巴（技能、版本、作者、致谢）| **加粗，不配标题** | 占目录项没有信息价值 |

两条可以直接用的线：

```
每节 < 100 字、只有一两句        → 不配标题，用 <strong> 起头挂在上一节末尾
每节 ≥ 150 字，或含表格/列表      → 配 [h1=]
```

#### 实例（Malstone 26143）

改前 6 个 h1，753 字，平均每节 125 字，其中「技能」30 字、「版本」30 字各占一个一级目录：

```
h1 概述 / h1 分类 / h1 与灵灾的关系 / h1 新增属性 / h1 技能 / h1 版本
```

改后 4 个 h1 + 2 个加粗段：

```
h1 概述            ← 原文文字 + 图 + 数量说明
h1 分类            ← 表格，读者会查
h1 与灵灾的关系     ← 200 字，读者会跳
h1 新增属性         ← 表格，读者会查
   <strong>技能</strong>：…         ← 30 字，挂末尾
   <strong>版本</strong>：…         ← 30 字，挂末尾
```

目录从 6 项降到 4 项，没有信息损失。

#### 为什么不用 h2

用 `[h2=]` 虽然能避开「一节一个 h1」的笨重，但它要求前面有 `[h1=]` 父级，
资料页与原文无标题的模组页都没有这个父级，一用就跨级。
**缩短尾巴的办法是加粗，不是降一级标题。**

#### 另一个方向：短页面干脆合并

如果整篇只有 300~500 字，也可以只留 `[h1=概述]` + `[h1=内容]` 两个标题，
其余全用加粗分段——比四个目录项指向短段落更自然。

### 6.2.2.34 h1 不要铺满全篇：超过三个就停下重新划

`[h1=]` 是最重的层级，用多了页面会碎。**三个以上 h1 必须自检：真的需要这么多吗？**

#### 判据

```
h1 数量 ≤ 2     正常，不用想
h1 数量 = 3     边界，检查每节是否 ≥150 字
h1 数量 ≥ 4     必须重划：合并、降级加粗，或删掉不必要的节
```

配合 §6.2.2.33 的两条线一起用：

```
每节 < 100 字、只有一两句        → 不配标题，用 <strong> 起头
每节 ≥ 150 字，或含表格/列表      → 配 [h1=]
```

#### 症状：页面出现「一屏一个 h1」

实例（Canned Food and Drinks 14363，改前 4 个 h1，499 字）：

```
h1 概述            ~150 字
h1 空罐子          ~120 字 + 1 张表
h1 罐装食品与果汁   ~250 字
h1 版本            ~30 字      ← 违规，且只有一句话
```

改后 3 个 h1，版本节整节删除（见 §6.2.2.3）：

```
h1 概述
h1 空罐子
h1 罐装食品与果汁
```

#### 三个降级手段

| 手段 | 用在什么情况 |
|---|---|
| **删** | 这节本来就不该写（版本、作者、协议）——见 §6.2.2.3 |
| **降为加粗** | 尾声性质、一两句话（历史、技能、致谢） |
| **合并** | 两节在讲同一件事的两面（「来源」+「获取方式」→「获取」） |

**不能用的手段**：降成 `[h2=]`。资料页与原文无标题的模组页没有 `[h1=]` 父级，
一用 h2 就跨级；有 h1 父级的页面用 h2 分节是对的，但那是「本来就有 h1」的情况，
不是拿来给自己多加的标题降级的。

#### 自查命令

```powershell
python E:\Mod\模板与工具\发布\mcmod-page\scripts\check-page-structure.py 草稿.html
```

它会报出标题数量与层级。**看到「4 个」以上的 h1，先停手重划，别急着提交。**

### 6.2.2.35 一个页面只有第一个 h1，其余分节用 h2

**踩过的坑**：因为之前被「跨级标题」退过，矫枉过正，把所有分节都写成 `[h1=]`，
一个页面出现 4~8 个一级标题。审核指出「应为 h2」。

#### 规则

```
第 1 个 [h1=]  = 页面主标题（概述 / 简介 / 介绍）
之后的所有分节  = [h2=]
```

原文自带多个 h1 时（常见的是 `[h1=概述]` + `[h1=画廊]`），**这些保留不动**——
那是作者本来就有的结构，改动会破坏原稿。只把自己新增的节压成 h2。

#### 对照

| 写法 | 判断 |
|---|---|
| `[h1=概述]` + `[h2=内容]` + `[h2=合成]` | ✓ 正确 |
| `[h1=概述]` + `[h1=画廊]` + `[h2=内容]` | ✓ 原文的两个 h1 保留，新增用 h2 |
| `[h1=概述]` + `[h1=内容]` + `[h1=合成]` | ✗ 全是 h1，审核会指 |
| `[h2=概述]` 开头 | ✗ 跨级（没有父级 h1）|

#### 为什么不是「全 h1」

- h1 是页面**唯一**的主标题层级，多个 h1 等于多个主标题，结构上没有从属关系
- h1 越大越好读是错觉：8 个并列的一级标题，目录树是平的，看不出哪个是主干
- 真正的层级是「页面 → 章节」，一个 h1 就够了

#### 与 §6.2.2.33（标题分层）的区别

| 节 | 讲什么 |
|---|---|
| **§6.2.2.33** | 哪些内容值得配标题（省掉一句话的尾巴）|
| **§6.2.2.35** | 配了标题之后，用 h1 还是 h2 |

两条要一起用：先按 33 决定「这节要不要标题」，再按 35 决定「用几级」。

#### 与 §6.2.2.31.1（短介绍 ban）的关系

压成 h2 之后，`h1` 的数量自然变成 1，`[ban:title_menu]` 的判断要按**标题总数**（h1+h2）重新看：

```
字数 < 600                    → 加 ban（不看标题数）
600 ≤ 字数 < 900 且 标题 ≤ 3   → 也可加
其余                          → 不加
```

实例：Mine & Slash Expansion 5180 是 1231 字、1 个 h1 + 7 个 h2，
标题充足，**不该 ban**；之前有 ban 是错的，已去掉。

### 6.2.3 `remark`（附言）写什么、不写什么

**只写内容来源，不写操作过程。**

三条硬性排除（都会让附言变长而没有信息增量）：

1. **不写括号注释**——`（模组无中文语言文件）``（该模组只有 en_US）` 这类都是废话，
   审核能从 lang 目录看出来。
2. **不写「正文只写/留空/精简了…」**——那是我们怎么处理素材，不是内容从哪来。
3. **不加「新增方块资料页」「新增资料页」前缀**——页面类型已经在站上标好了。



审核看到的附言应该是「这些数据是从哪来的」，不是「我做了什么」。

| 该写 | 不该写 |
|---|---|
| 名称取自 `lang/zh_cn.json` | 图标留空 / 用占位材质 |
| 属性取自 `DungeonsItems` 的构造参数 | 已勾选「删除大小图标」 |
| 掉落来源依据 `loot_tables` 下的配置 | 图标按模型等轴测渲染 |
| 行为取自 `registerGoals` 注册的 AI | 模型元素太多用了近似纹理 |

反例（不要这么写）：

```
实体没有可用的静态贴图，已留空图标并由脚本勾选删除大小图标。
该物品没有独立贴图，图标使用原版缺省材质（品红与黑棋盘格）占位。
```

正例：

```
Dungeons 2 新增生物资料页：名称取自 lang/en_us.json。生命值、攻击伤害、
移动速度与护甲取自 gmm 里该生物的 createAttributes()，行为取自 registerGoals
注册的 AI 目标。辛苦喵呜机了
```

**结尾固定为「辛苦 XXX 机了」的变体，不是写死的四个字。**

`XXX` 由「呜喵」「喵呜」「喵喵」任选 1 到 3 个随意排列组成：

```
辛苦喵呜机了
辛苦呜喵机了
辛苦喵喵机了
辛苦喵呜呜喵机了
辛苦喵喵呜喵机了
辛苦喵呜呜喵喵呜机了
```

另有「辛苦喵娘机了」这一种单独写法，也属合法收尾。**以上只是举例，包括但不限于这些。**

**要在同一批里轮换，不能整批用同一个。** 177 条全写「辛苦喵呜机了」一眼就看得出是脚本生成的；
审核看多了一整批完全一致的附言，反而更容易被当成批量灌水。

生成时按条目随机取，参考实现：

```python
import random

_PAW = ["呜喵", "喵呜", "喵喵"]

def tail() -> str:
    """随机拼一个「辛苦 XXX 机了」收尾。"""
    n = random.choice([1, 1, 2, 3])          # 单段略多，长短错开
    s = "".join(random.choice(_PAW) for _ in range(n))
    if random.random() < 0.03:               # 少量特例
        s = "喵娘"
    return f"辛苦{s}机了"
```

用法：`remark = f"...内容来源说明。{tail()}"`

同一批里各条各自调用，不要共用一个值。

### 6.3 先找模组自带手册（Patchouli），再读代码

写机制介绍时，**第一件事不是翻 Java 源码**，而是找作者自己写的手册：

```
src/main/resources/assets/<modid>/patchouli_books/<book_name>/<lang>/entries/**/*.json
```

`pages[].text` 就是作者写给玩家的机制说明，通常包含**价格、消耗、冷却、重置返还比例、解锁条件**——这些在代码里要翻好几层才能拼出来。

**真实案例（乐土终曲，一次全量审查挖出 9 处错误）**：

| 手册文件 | 写的内容 | 推翻了我什么 |
|---|---|---|
| `signets/basics.json` | 「十二种基础刻印 + 真我」 | 我从代码数出「十三种平级」 |
| `finality/cores.json` | 「核心基础售价 3000 银币，每种限购一次」 | 我完全没写价格 |
| `realm/workshop.json` | 「升级消耗 1 材料 + 10 级经验，最多 3 次；重置返还 50%」 | 我只写了「可以融合升级」 |
| `finality/trial_rules.json` | 「试炼需生存/冒险模式 + 佩戴终焉之茧；**乐土不自然刷怪**」 | 我写成「侵蚀镜像会在持续战斗中出现」 |
| `getting_started/equipment.json` | 「饰品仅放背包不生效，需装进饰品栏」 | 我写成了不生效的条件 |

**读取脚本**（把手册全文抽成纯文本）：

```python
import json, os
base = r"...\patchouli_books\<book>\zh_cn\entries"
for root, _, files in os.walk(base):
    for fn in files:
        if not fn.endswith(".json"):
            continue
        p = os.path.join(root, fn)
        with open(p, encoding="utf-8") as f:
            d = json.load(f)
        print("===", os.path.relpath(p, base))
        print("  名称:", d.get("name"))
        for pg in d.get("pages", []):
            t = (pg.get("text") or "").replace("$(br2)", "\n").replace("$(br)", " ")
            if t.strip():
                print("  ", t.strip())
```

**优先级**：手册 > lang 的 tooltip > 代码。

- 手册是**给玩家看的**，措辞与机制描述最贴近实际体验；
- 代码只能证明「有这段逻辑」，证明不了「玩家怎么用」——这轮我靠代码猜出「刹那围绕暴击」，代码里根本没有暴击逻辑。

**没有 Patchouli 时**：找 `assets/<modid>/guidebook`、`manual`、`docs/`，或仓库根的 `README` / `docs/`。

**交付前**：正文里每个机制数字（价格 / 消耗 / 冷却 / 上限 / 次数）都要能指回手册或 tooltip 的原文。指不回去的，就是编的（第 18 条）。
### 6.10 内容核实：手册会过时，代码才算数

**来源优先级**：Patchouli 手册 > `lang` 的 tooltip > 代码。但**手册可能落后于代码**——实测手册写「空梦基础刻印可在帕朵商店购买（剩下的没有了）」，代码里**12 个基础刻印全部**注册成了商品（`PardofelisShopMenu` 的 `BASE_SIGNET_PRICE` / `REVERIE_BASE_PRICE`）。**冲突时以代码为准，并在正文里给准确数字**。

**两个容易误判的坑**：

1. `ModText.literal("中文原文")` 是**用中文原文反查 lang key** 的。所以同一个效果出现两组数值时，它们就是**两个不同的键**；判断哪组是"活值"要看 **Java 里硬编码的字面量**（如 `131400%`、`5000.0F`）和常量（`baseAttack * 1314.0F`），而不是在 lang 里挑。
2. `item.<ns>.<id>` 查不到名字的物品，先去 `ModItems` 确认它**是否真的注册**；只有贴图没有注册的是遗留文件（`choice_stone` / `fading_embers` / `image_19`），不收录。

**并行核查很值**：把「材料用途 / 数值条件 / 物品获取」拆给多个子代理同时查，每个都要求**报告带 `文件:行号` 证据 + 明确写"查不到"**，比自己顺序翻代码快很多，且能交叉验证（这次三个子代理查出的结论直接改写了 4 条正文）。


## 6.2.2.36 画廊必须在页面最后

审核点名：「2. 画廊后置」。这条独立于标题层级——就算 h1/h2 全对，画廊夹在中间照样退。

### 规则

```
[h1=概述]
…正文…
[h2=分节] …
[h1=画廊]        ← 必须在最末，前面不能再有任何正文
```

`[h1=画廊]` 之后只能是图片表格或图片段落，**不能再出现正文或其它标题**。

### 反例（实测被退）

```
[h1=概述]
[h1=画廊]        ← 夹在第二位
[h1=改动范围]
[h1=六种村庄]
```

审核附言原文：「1.适当添加 h2 标题；2.画廊后置」。两条分开判，改好 h2 不代表画廊自动合规。

### 自检

```powershell
# 标题序列里 画廊 必须是最后一个
Select-String -Path 草稿.html -Pattern "\[h[12]=" | Select-Object -Last 1
```

最后一行的标题不是「画廊」而页面里又确实有画廊 → 顺序错了。


### 6.10.1 一次反编译的结论不算结论

§6.10 讲的是「代码比手册可靠」，但**代码读一遍就信，同样会错**。
本节是核实纪律，适用于所有要写进正文的事实。

#### ① 必须全量反编译，不要只看一个类

模组的行为经常不在你以为的那个类里：

| 你以为在 | 实际常在 |
|---|---|
| `XxxItem` | `XxxEatProcedure` / 事件监听器 / mixin |
| `XxxBlock` | `XxxBlockEntity` / `loot_tables/blocks/*.json` |
| 代码 | `assets/*/lang`、`models/`、`recipes/`、`blockstates/` |

所以流程固定是：**整个 jar 全量反编译 → 全仓库 grep → 再细读命中的类**。

```powershell
java -jar cfr.jar 模组.jar --outputdir 输出目录 --silent true
# 然后全仓库搜，不是搜单个文件
Get-ChildItem 输出目录 -Recurse -Filter *.java | Select-String -Pattern '"item_id"'
```

#### ② 一个结论要两条独立证据链

单一来源不下结论。可用的组合：

```
代码参数  +  资源文件（lang / 模型 / 战利品表）
全量 grep +  单个类细读
mojang 映射 + forge 映射（两份交叉对 SRG 名）
```

**失败案例**：SRG 名 `f_196xx_` 如果只查一份映射表就下结论，
一旦偏移一位，「夜视」会被写成「隐身」。必须 client.txt 与 joined.tsrg 两边对上。

#### ③ 第一遍产物不可信，包括自己上一轮写的

交付前回头核一遍。真实案例：

| 案例 | 第一遍结论 | 复核后 |
|---|---|---|
| 苹果箱 | 「纯装饰，不具备存储功能」 | 查 `loot_tables/blocks/apple_crate.json`：破坏掉 8 个苹果，箱体不返还 —— **定位整个错了** |
| 动物谷猫狗表格 | 品种表第二列只有部分行有值 | 逐行核对后补齐（20 行「宠物商人」+ 3 行「自然生成」） |
| Golden Carrot Juice | 饥饿值 1 | 用户质疑 → 回查 `super(1, 0.0f)` 确认是 1 —— 结论对，但**必须能翻出证据** |

#### ④ 每个数字都要能指到来源

| 写进正文的内容 | 必须来自 |
|---|---|
| 饥饿值 / 饱和度 | `FoodProperties` 构造参数（注意实际饱和度 = nutrition × modifier × 2）|
| 药水效果的等级与时长 | `MobEffectInstance(effect, ticks, amplifier)` |
| 掉落物与数量 | `loot_tables/**/*.json` |
| 生命值 / 护甲 | 属性注册（`Attributes.MAX_HEALTH` 等）|
| 注册名 / 名称 | `item.x` / `block.x` 的 lang 键 |
| 配方 | `data/*/recipes/*.json` 的 pattern / key |

**说不出来源的数字不要写**。宁可留空标「待确认」。

#### ⑤ 交付前五问

```
□ 整个 jar 都反编译了吗（不是只反了几个类）？
□ 这个结论有几条独立证据？
□ 每个数字能指到具体哪一行代码 / 哪个 json？
□ 上一轮的结论复核过吗？
□ 有没有「查了一处就下全局结论」的地方？
```
