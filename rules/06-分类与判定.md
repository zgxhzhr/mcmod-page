### 6.2 专有名词必须查 lang 文件，不能从代码标识符翻译

写模组介绍时，物品名、机制名、刻印名一律以 `src/main/resources/assets/<modid>/lang/zh_cn.json` 为准。

**反例（真实踩过，一次错了 8 个名字）**：

| 代码标识符 | 直译（错） | lang 实际名（对） |
|---|---|---|
| `signet_of_reverie` | 追忆 | **空梦** |
| `signet_of_bodhi` | 菩提 | **天慧** |
| `signet_of_daybreak` | 天启 | **旭光** |
| `signet_of_decimation` | 抽离 | **鏖灭** |
| `signet_of_deliverance` | 救赎 | **救世** |
| `fenghuang_down` | 凤凰下 | **羽渡尘** |
| `abyss_flower` | 深渊之花 | **黑渊白花** |
| `paintbrush` | 画笔 | **绘世之笔** |
| `whisper_of_the_past` | 往昔低语 | **往世的飞花·爱之诗** |

**为什么必须查**：代码里的注册名是开发者起的内部标识（`signet_of_bodhi`），玩家看到的是 lang 里的名字（**天慧**）。两者经常对不上——`bodhi` 字面是「菩提」，但崩坏3 设定里这个刻印叫「天慧」。**不查 lang 就写介绍，等于在编名字**（第 18 条：内容不实）。

**连带效果也要用代码验证**：名字对了，效果未必对。同一个类里可能有多条效果，容易张冠李戴。例如 `BodhiSignetSystem` 里既有 `reduction`（减伤）又有 `HEAVENLY_EYE_VULNERABILITY`（易伤）和 `NBT_PASSIVE_DAMAGE_ENABLED`（开眼被动），lang 里的「天慧·开眼」证明**开眼才是主体**，减伤是另一条「真我无我」的效果。

**核对脚本**：

```powershell
$zh = "src/main/resources/assets/<modid>/lang/zh_cn.json"
$c  = Get-Content $zh -Raw -Encoding UTF8
foreach ($key in @('item.yourmod.xxx', 'item.yourmod.yyy')) {
    $m = [regex]::Match($c, '"' + [regex]::Escape($key) + '"\s*:\s*"([^"]*)"')
    if ($m.Success) { Write-Output ("{0,-30} {1}" -f $key, $m.Groups[1].Value) }
    else            { Write-Output ("{0,-30} （无此键）" -f $key) }
}
```

**顺带能挖到的东西**：lang 里常藏着机制描述（`text.<modid>.literal.*`），比如「佩戴追忆之证时，对撕裂状态生物伤害提高 15%」这类具体数值——比读代码更快理解玩法。

**交付前必做**：把正文里出现的每个专有名词与 lang 逐条对照，残留错名要清零。

#### 双语字典必须分开查：zh_cn 取主要名称、en_us 取次要名称（2026-11-17 实测）

29737 的 12 条 BUFF 全把中文名写进了「次要名称」，原因是一行查表代码在**中文**字典里找「英文名」：

```python
# ✗ 错：lang 是 zh_cn，命中的永远是中文
en_nm = next((v for k, v in lang.items() if k.endswith(f"effect.orcinvasion.{eid}")), None)

# ✓ 对：en_us 单独加载，取不到就报错（不要静默回退到中文）
EN = json.loads(z.read("assets/<modid>/lang/en_us.json").decode("utf-8"))
en_nm = EN.get(f"effect.orcinvasion.{eid}", "")
if not en_nm:
    raise SystemExit(f"✗ {eid} 在 en_us 里没有名字")
```

**为什么必须报错而不是留空**：静默留空会把问题推到审核；直接抛错能在生成阶段拦住整批。

**通用做法（任何批次，生成名称前先跑一次）**：

```python
zh = json.loads(z.read("assets/<ns>/lang/zh_cn.json").decode("utf-8"))
en = json.loads(z.read("assets/<ns>/lang/en_us.json").decode("utf-8"))
for key in zh:                      # 只遍历一个字典，避免对齐错位
    short = key.split(".", 2)[-1]
    base = {"item": "item.<ns>.", "entity": "entity.<ns>.", "effect": "effect.<ns>."}
    zh_v, en_v = zh.get(key), en.get(key)
    if zh_v and not en_v:
        print("缺英文名:", key, zh_v)   # 这类要么补规则要么留空 ename
```

**自检三问**：

```
□ name 与 ename 有没有完全相同的行？（相同即错，audit 会阻断）
□ ename 里有没有中文字符？（有即错）
□ 有没有哪条 ename 是靠「查不到就回退」得到的？（回退来的都不算数）
```

`audit-delivery.py` 已内置「主次名称相同即阻断」；中文出现在 ename 属同类，一并按该条处理。

### 6.2.1 没有官方中文名时：只写英文，不要自己翻译

**判定顺序**：

1. 先找 `lang/zh_cn.json`——有就用它的译名（这是 §6.2）；
2. **完全没有 zh_cn.json，或者该物品的键在 zh_cn 里查不到** → **不要自己译**，
   主要名称直接写英文原名（如 `Kelp Salad`、`Broken Amethyst Shard`），
   **次要名称留空**（`ename` 不要填）。

自己译的名字会和玩家在游戏里看到的对不上，也容易被审核当作错误译名退回。

```json
// ❌ 自己译（模组没有 zh_cn）
{ "name": "海带沙拉", "ename": "Kelp Salad" }

// ✅ 只写英文，ename 留空
{ "name": "Kelp Salad", "ename": "" }
```

例外：页面标题若已在站点上形成惯例（例如同系列 5 个装备页都叫 `XXX Exosuit 套装`），
沿用站点写法，不要为了纯英文去改动已有惯例。

### 6.2.2 装饰方块的抽象父资料命名：`XX装饰方块` / `XX Blocks`

**来源**：审核附言（2026-11-16）+ 站上真实页面校正（2026-11-17，日光石装饰方块）——

> 【附言：补充：装饰方块的名称为格式 "XX 装饰方块（XX Block）" ~】

**关键**：附言里的括号是**审核员的说明性括注**，不是要写进名字的括号；站上实例也不带括号。
真实页面（classId 1040926 一带）：

```
主要名称：日光石装饰方块        次要名称：Heliostone Blocks
下辖 5 个物品/方块：日光石、不稳定的日光石、日光石楼梯、日光石台阶、日光石墙
```

**口径**：只管**抽象父资料（综合页）**的命名，不是让每个装饰方块子条目改名。

```json
// 抽象父资料（综合一批装饰方块）
{ "name": "XX装饰方块", "ename": "XX Blocks", "regname": "", "icon32": "", "icon128": "" }

// 子资料：保持 lang 本名，不加后缀（§6.2）
{ "name": "冬瓜蜡烛", "ename": "Wax Pipe Candle", "html": "" }
```

- `name` = 系列名 + `装饰方块`，**中间不留空格、不加括号**；`ename` = 系列英文名 + ` Blocks`（**复数**）
- 「XX」取系列名（该组共有的那个词，lang 里的写法），不是注册名
- 父资料照综合页规则留空注册名与图标，子资料带 `"html": ""`
- 装饰方块以外的分类（建筑方块、功能方块、食物…）的父资料不套这个后缀
- 系列名本身已带「方块」时避免叠字，按系列名 + `Blocks` 处理并在交付说明里注明

**历史批次待改（只在下一次动到这些页时顺带改，不单独回退）**：

```
30083 sea_old_stone  → Old Stone（未带装饰方块后缀、ename 空）
30083 demon_stone    → Demon Stone
30083 building_props → Building Props
9667  sea_creep_head / sea_creep_trophy → 同（英文名当主名，缺 ename）
```

### 6.2.3 工具套具的抽象父资料命名：`XX 套具（XX Kit）`

**来源**：审核附言（2026-11-16，某模组四条工具同日被退）——

> 【附言：原版的标准四件套需要创建综合资料 "XX 套具 (XX Kit) " ~】

**口径**：同样是**抽象父资料**的命名，不是给单件工具改名：

```json
// 抽象父资料（综合 斧/锄/镐/锹 四条）
{ "name": "XX套具", "ename": "XX Kit", "regname": "", "icon32": "", "icon128": "" }

// 子资料：保持 lang 本名，不加「套具」后缀（§6.2）
{ "name": "Emerald Axe", "ename": "", "html": "" }
```

- **剑不并入套具**，单独成页（2026-11-16 口径）
- 只收原版标准四件套（斧 / 锄 / 镐 / 锹）；模组自创工具形态（镰刀、锤、大剑…）按 §6.1.10 另行判定
- 综合的判定与流程见 `rules/05 §6.1.10`（父资料先写 → 提交 → 综合 → 子资料清正文）
- 盔甲套装沿用站点既有写法，不套「套具」（§6.2.1 例外条款）

#### 套装类父页：主要名称 `XX套装`、次要名称 `XX Suit`——括号不进名字（2026-11-17 站内实例终版）

站内实例（用户截图，物品 265609）：

```
主要名称：星烁合金套装        次要名称：Star Shimmer Suit
物品类型：装备（套装）
别名(中)：星烁合金装备、星烁合金套      别名(英)：Star Shimmer Armor Set、Star Shimmer Armor
```

**规则**：

- 审核附言 `"XX 套具 (XX Kit)"` 里的括号是**译文标注**，不是名字的一部分——
  主要名称只写 `XX套装`（或站点既有的 `XX套具`），英文名进「次要名称」字段
- 同一写法适用**所有**综合父资料/概念页：`企鹅帽` + `Penguin Hats`，绝不写 `企鹅帽 (Penguin Hats)`
- 站点物品类型显示「装备（套装）」：一级是「装备」，「套装」只是类型标注；batch 的 category 填「装备」
- 中英双别名站点支持但非必须；主/次名称成对（§6.2.4）才是硬要求

#### 装备综合按「套」切分，不跨套合大组（2026-11-17 用户口径，9120 实测）

一个模组里常有**多套互相独立的装备线**（不同材料、不同槽位组合）。综合父资料
**按套各建一个**，不许把几十件装备塞进一个「XX 装备」大杂烩：

```
✗ 「企鹅装备」1 父吞 22 件（帽子+皮套+火焰套+云靴混在一张表里）
✓ 「企鹅帽」14 件一父 · 「企鹅套装」3 件一父 · 「火焰企鹅套装」4 件一父 ·
   落单的一件（云企鹅靴）逐条——凑不成套的不硬并
```

**装备类综合的优先级：成套 > 部位组（须说明）**（2026-11-17 用户三改定稿，9120）：

1. **能按套切就先按套**：同一材料线、一起穿戴的（企鹅套装 3 件、火焰企鹅套装 4 件）各建一父；
2. **凑不成套的同部位同类**（如 14 顶企鹅帽——每顶属不同品种线，只有头盔一个栏位，
   没有对应的胸/腿/靴）可以按部位组综合，但**必须向用户说明理由**：
   - 父资料 remark 声明句后紧跟一句「综合理由：不成套（…）」
   - README 类型核对处写明为什么这组不按套切
   判例来源：29737 刷怪蛋（57 枚同槽位）、7663 羽毛系列——同功能仅目标/颜色不同的组，
   逐条正文必然模板化，表格反而承载全部独有数据（材料、对应品种）。
3. **单件不硬并**：云企鹅靴只有一件靴子，逐条。

```
材料类（羽毛/蛋）→ 可成组综合（7663 羽毛系列、29737 刷怪蛋先例成立）
装备成品        → 只有「套」能当父资料；不成套的逐条，单件绝不硬并
```

判据：**同一套 = 同一材料线，且通常一起穿戴**。跨套合并后，表格「备注」列
若全在解释「这其实是另一套」，就是切分信号（9120 实例即如此）。

### 6.2.4 抽象父资料的中英名称必须成对写（2026-11-16 审核附言）

> 【附言：次要名称也要写（Souled Ignitium Suit）】

某模组的「Souled Ignitium 套装」父资料**已通过审核**，但审核员补了一句：次要名称（英文）也不能空。

**口径**：

| 页面 | 主要名称 | 次要名称（ename） |
|---|---|---|
| 抽象父资料（套装 / 套具 / 整族汇总） | `XX 套装` / `XX 套具` | **必填**：`XX Suit` / `XX Kit` |
| 普通物品页（模组有 zh_cn） | 中文名 | 英文名（能查出就写） |
| 普通物品页（模组无 zh_cn） | 英文名 | 留空（§6.2.1） |

也就是说：**父资料的英文名不是可选装饰，是必填项**——父资料本身没有注册名可查，
英文名是读者唯一能对外检索的标识。子资料按普通物品规则处理。

**脚本与 JSON 都不用改**：`ename` 字段本来就存在，批量脚本的 `clearOrSet(qm('ename'), …)`
会照写；缺的只是生成 JSON 时没给父资料填值。`preflight.py` 对父资料会对空 ename 给提醒。

## 11 模组分类（用法）

每个模组有一个**官方主分类**（单值，不是多选标签）。已存进 `mcmod.db` 的 `classes.category` 字段，
覆盖 31,164 / 32,273 个模组（96.6%），其余 1,109 个是原版/特殊页面。

### 11.1 分类与处理优先级

| 分类 | 处理 | 理由 |
|---|---|---|
| **LIB** | **排除** | 前置库，20 字介绍就是完整的 |
| **魔改** | **排除** | 整合包/修改器，同上 |
| **辅助** | **排最后** | 功能单一，内容天然少 |
| 科技 / 魔法 / 冒险 / 农业 / 装饰 / 实用 | 正常处理 | 主体内容类 |

分类 id（抓取脚本用，日常不需要）：1=科技 2=魔法 3=冒险 4=农业 5=装饰 7=LIB 21=魔改 23=实用 24=辅助。

### 11.2 常用查询

```sql
-- 短页面待处理（排除 LIB/魔改，辅助排最后）
SELECT id, name, category, chars FROM classes
WHERE chars < 100
  AND COALESCE(category,'') NOT IN ('LIB','魔改')
ORDER BY (category='辅助'), chars;

-- 按分类统计短页面
SELECT COALESCE(category,'(未分类)') 分类, COUNT(*) 数量
FROM classes WHERE chars < 100
GROUP BY category ORDER BY 数量 DESC;

-- 只处理内容类模组
SELECT id, name, chars FROM classes
WHERE chars < 300 AND category IN ('科技','魔法','冒险','农业','装饰','实用')
ORDER BY chars;
```

### 11.3 短页面分类分布（chars<100 实测）

| 分类 | 数量 | 分类 | 数量 |
|---|---|---|---|
| 辅助 | 1,922 | 农业 | 227 |
| 实用 | 1,108 | 科技 | 158 |
| 冒险 | 548 | 魔改 | 149 |
| 装饰 | 491 | 魔法 | 111 |
| LIB | 430 | 未分类 | 260 |

**排除 LIB（430）+ 魔改（149）后，待处理 4,825 条**（辅助 1,922 条排最后）。

分类是怎么抓的、踩了哪些坑，见 `scripts/category-crawl.py` 的 docstring（一次性任务，不复用）。

## 12 短页面批量判定（LLM 分类）

给成千上万个「短页面」决定「**要不要人工重写介绍**」，靠规则做不到（关键词误判率高），靠 LLM 可以。

### 12.1 判据（三版演化，最后一版才是对的）

| 版本 | 判据 | 剔除数 | 问题 |
|---|---|---|---|
| v1 | 「有没有讲清功能」| 1,118 | 判据错了：讲清了但没新东西的模组也留下了 |
| v2 | 「有没有新增物品/方块/机制」| **2,321** | 矫枉过正：「联动」「附属」被一刀切判成无内容 |
| **v3** | 「明确是减法/纯工程才剔除，模糊一律保留」| **1,105** | ✅ 采用 |

**v2 → v3 的教训**（用户实测误伤后修正）：

| 正文 | v2 判定 | 正确判定 | 为什么 |
|---|---|---|---|
| 「为农夫乐事与婴儿肥**添加了联动**」| 剔除 | **保留** | 联动通常带新物品/配方 |
| 「环境科技-发电机」| 剔除 | **保留** | 科技模组的机器，有具体内容 |
| 「移除玩家受伤动画」| 剔除 | 剔除 ✓ | 明确减法 |
| 「实现了 X 与 Y 的兼容」| 剔除 | 剔除 ✓ | 纯兼容补丁 |

**核心原则：宁可多留，不可误杀。** 漏掉一个有内容的模组（要人工重写），比多留一个没内容的（浪费几分钟）代价大得多。

### 12.2 判据完整清单（v3）

**剔除（必须能从正文明确判断）**：
- 明确说「移除/禁用/关闭/隐藏/删除」某原版功能
- 明确说「修复了 XX Bug」
- 明确说「是 X 的移植版/重置版/分支版/翻译版」且无新增说明
- 明确说「是前置库/Lib/API」
- 明确说只调数值/性能（「燃烧更快」「伤害更高」），无新物品
- 明确说「仅实现 X 与 Y 的兼容」

**保留（有新增内容）**：
- 说「添加/新增/加入」任何东西
- 说「为 X 与 Y 添加了**联动**」
- 是某个模组的**附属/扩展/内容包**
- 提到具体物品名/方块名/机制名/数值/数量

**待定**：一句话且既没说新增、也没说移除/修复/移植。

### 12.3 性能：67 条/秒 的关键

**三个坑，一个都不能踩：**

**① 模型选择：必须用 `deepseek-chat`，不能用 `deepseek-flash`**

`deepseek-flash` 是**推理模型**，会先输出 `reasoning_content`（思考过程）占用 token 预算。
批量判断时思考特别长（4000 token 都打不住），导致 `content` 返回空字符串，看起来"API 成功但结果为空"。

```python
# 症状
{"finish_reason": "length", "content": "", "reasoning_content": "We need answer Chinese..."}
```

单条判断时思考短，碰巧能出结果，所以这个坑很隐蔽。

**② 批量：一次判断 10 条**

```python
# 单条：4,791 次请求
# 批量 10 条：480 次请求 → 快 8-10 倍
items = "\n".join(f'{i}. id={r["id"]} 《{r["name"]}》: {r["preview"][:120]}' for i, r in enumerate(batch, 1))
```

**③ `response_format=json_object` 要求返回对象，不能是数组**
