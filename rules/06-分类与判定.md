### 6.2 专有名词必须查 lang 文件，不能从代码标识符翻译

写模组介绍时，物品名、机制名、刻印名一律以 `src/main/resources/assets/<modid>/lang/zh_cn.json` 为准。

**反例（真实踩过，一次错了 8 个名字）**：

| 代码标识符 | 直译（错） | lang 实际名（对） |
|---|---|---|
| `signet_of_reverie` | 追忆 | **空梦** |
| `signet_of_bodhi` | 菩提 | **天慧** |
| `signet_of_daybreak` | 天启 | **旭光** |
| `signet_of_decimation` | 抽离 | **鏖灭** |
| `signet_of_deliverance` | 救赎 | **救世** |
| `fenghuang_down` | 凤凰下 | **羽渡尘** |
| `abyss_flower` | 深渊之花 | **黑渊白花** |
| `paintbrush` | 画笔 | **绘世之笔** |
| `whisper_of_the_past` | 往昔低语 | **往世的飞花·爱之诗** |

**为什么必须查**：代码里的注册名是开发者起的内部标识（`signet_of_bodhi`），玩家看到的是 lang 里的名字（**天慧**）。两者经常对不上——`bodhi` 字面是「菩提」，但崩坏3 设定里这个刻印叫「天慧」。**不查 lang 就写介绍，等于在编名字**（第 18 条：内容不实）。

**连带效果也要用代码验证**：名字对了，效果未必对。同一个类里可能有多条效果，容易张冠李戴。例如 `BodhiSignetSystem` 里既有 `reduction`（减伤）又有 `HEAVENLY_EYE_VULNERABILITY`（易伤）和 `NBT_PASSIVE_DAMAGE_ENABLED`（开眼被动），lang 里的「天慧·开眼」证明**开眼才是主体**，减伤是另一条「真我无我」的效果。

**核对脚本**：

```powershell
$zh = "src/main/resources/assets/<modid>/lang/zh_cn.json"
$c  = Get-Content $zh -Raw -Encoding UTF8
foreach ($key in @('item.yourmod.xxx', 'item.yourmod.yyy')) {
    $m = [regex]::Match($c, '"' + [regex]::Escape($key) + '"\s*:\s*"([^"]*)"')
    if ($m.Success) { Write-Output ("{0,-30} {1}" -f $key, $m.Groups[1].Value) }
    else            { Write-Output ("{0,-30} （无此键）" -f $key) }
}
```

**顺带能挖到的东西**：lang 里常藏着机制描述（`text.<modid>.literal.*`），比如「佩戴追忆之证时，对撕裂状态生物伤害提高 15%」这类具体数值——比读代码更快理解玩法。

**交付前必做**：把正文里出现的每个专有名词与 lang 逐条对照，残留错名要清零。
### 6.2.1 没有官方中文名时：只写英文，不要自己翻译

**判定顺序**：

1. 先找 `lang/zh_cn.json`——有就用它的译名（这是 §6.2）；
2. **完全没有 zh_cn.json，或者该物品的键在 zh_cn 里查不到** → **不要自己译**，
   主要名称直接写英文原名（如 `Kelp Salad`、`Broken Amethyst Shard`），
   **次要名称留空**（`ename` 不要填）。

自己译的名字会和玩家在游戏里看到的对不上，也容易被审核当作错误译名退回。

```json
// ❌ 自己译（模组没有 zh_cn）
{ "name": "海带沙拉", "ename": "Kelp Salad" }

// ✅ 只写英文，ename 留空
{ "name": "Kelp Salad", "ename": "" }
```

例外：页面标题若已在站点上形成惯例（例如同系列 5 个装备页都叫 `XXX Exosuit 套装`），
沿用站点写法，不要为了纯英文去改动已有惯例。

## 11 模组分类（用法）

每个模组有一个**官方主分类**（单值，不是多选标签）。已存进 `mcmod.db` 的 `classes.category` 字段，
覆盖 31,164 / 32,273 个模组（96.6%），其余 1,109 个是原版/特殊页面。

### 11.1 分类与处理优先级

| 分类 | 处理 | 理由 |
|---|---|---|
| **LIB** | **排除** | 前置库，20 字介绍就是完整的 |
| **魔改** | **排除** | 整合包/修改器，同上 |
| **辅助** | **排最后** | 功能单一，内容天然少 |
| 科技 / 魔法 / 冒险 / 农业 / 装饰 / 实用 | 正常处理 | 主体内容类 |

分类 id（抓取脚本用，日常不需要）：1=科技 2=魔法 3=冒险 4=农业 5=装饰 7=LIB 21=魔改 23=实用 24=辅助。

### 11.2 常用查询

```sql
-- 短页面待处理（排除 LIB/魔改，辅助排最后）
SELECT id, name, category, chars FROM classes
WHERE chars < 100
  AND COALESCE(category,'') NOT IN ('LIB','魔改')
ORDER BY (category='辅助'), chars;

-- 按分类统计短页面
SELECT COALESCE(category,'(未分类)') 分类, COUNT(*) 数量
FROM classes WHERE chars < 100
GROUP BY category ORDER BY 数量 DESC;

-- 只处理内容类模组
SELECT id, name, chars FROM classes
WHERE chars < 300 AND category IN ('科技','魔法','冒险','农业','装饰','实用')
ORDER BY chars;
```

### 11.3 短页面分类分布（chars<100 实测）

| 分类 | 数量 | 分类 | 数量 |
|---|---|---|---|
| 辅助 | 1,922 | 农业 | 227 |
| 实用 | 1,108 | 科技 | 158 |
| 冒险 | 548 | 魔改 | 149 |
| 装饰 | 491 | 魔法 | 111 |
| LIB | 430 | 未分类 | 260 |

**排除 LIB（430）+ 魔改（149）后，待处理 4,825 条**（辅助 1,922 条排最后）。

分类是怎么抓的、踩了哪些坑，见 `scripts/category-crawl.py` 的 docstring（一次性任务，不复用）。

## 12 短页面批量判定（LLM 分类）

给成千上万个「短页面」决定「**要不要人工重写介绍**」，靠规则做不到（关键词误判率高），靠 LLM 可以。

### 12.1 判据（三版演化，最后一版才是对的）

| 版本 | 判据 | 剔除数 | 问题 |
|---|---|---|---|
| v1 | 「有没有讲清功能」| 1,118 | 判据错了：讲清了但没新东西的模组也留下了 |
| v2 | 「有没有新增物品/方块/机制」| **2,321** | 矫枉过正：「联动」「附属」被一刀切判成无内容 |
| **v3** | 「明确是减法/纯工程才剔除，模糊一律保留」| **1,105** | ✅ 采用 |

**v2 → v3 的教训**（用户实测误伤后修正）：

| 正文 | v2 判定 | 正确判定 | 为什么 |
|---|---|---|---|
| 「为农夫乐事与婴儿肥**添加了联动**」| 剔除 | **保留** | 联动通常带新物品/配方 |
| 「环境科技-发电机」| 剔除 | **保留** | 科技模组的机器，有具体内容 |
| 「移除玩家受伤动画」| 剔除 | 剔除 ✓ | 明确减法 |
| 「实现了 X 与 Y 的兼容」| 剔除 | 剔除 ✓ | 纯兼容补丁 |

**核心原则：宁可多留，不可误杀。** 漏掉一个有内容的模组（要人工重写），比多留一个没内容的（浪费几分钟）代价大得多。

### 12.2 判据完整清单（v3）

**剔除（必须能从正文明确判断）**：
- 明确说「移除/禁用/关闭/隐藏/删除」某原版功能
- 明确说「修复了 XX Bug」
- 明确说「是 X 的移植版/重置版/分支版/翻译版」且无新增说明
- 明确说「是前置库/Lib/API」
- 明确说只调数值/性能（「燃烧更快」「伤害更高」），无新物品
- 明确说「仅实现 X 与 Y 的兼容」

**保留（有新增内容）**：
- 说「添加/新增/加入」任何东西
- 说「为 X 与 Y 添加了**联动**」
- 是某个模组的**附属/扩展/内容包**
- 提到具体物品名/方块名/机制名/数值/数量

**待定**：一句话且既没说新增、也没说移除/修复/移植。

### 12.3 性能：67 条/秒 的关键

**三个坑，一个都不能踩：**

**① 模型选择：必须用 `deepseek-chat`，不能用 `deepseek-flash`**

`deepseek-flash` 是**推理模型**，会先输出 `reasoning_content`（思考过程）占用 token 预算。
批量判断时思考特别长（4000 token 都打不住），导致 `content` 返回空字符串，看起来"API 成功但结果为空"。

```python
# 症状
{"finish_reason": "length", "content": "", "reasoning_content": "We need answer Chinese..."}
```

单条判断时思考短，碰巧能出结果，所以这个坑很隐蔽。

**② 批量：一次判断 10 条**

```python
# 单条：4,791 次请求
# 批量 10 条：480 次请求 → 快 8-10 倍
items = "\n".join(f'{i}. id={r["id"]} 《{r["name"]}》: {r["preview"][:120]}' for i, r in enumerate(batch, 1))
```

**③ `response_format=json_object` 要求返回对象，不能是数组**

```python
# ❌ 直接要求数组 → 返回空
'输出 JSON 数组: [{"n":1,"type":"X"}]'
# ✅ 包一层对象
'输出 JSON 对象: {"results":[{"n":1,"type":"X"}]}'
```

**实测对比**：

| 配置 | 速度 | 备注 |
|---|---|---|
| flash 单条 25 并发 | 1.07 条/秒 | 4,791 条约 75 分钟 |
| chat 批量 10 条 12 并发 | **67 条/秒** | 4,791 条约 **1.2 分钟** |

**62 倍差距。**

### 12.4 用法

```powershell
# 全量（自动跳过已判定的，支持断点续跑）
& $py "scripts\judge-batch.py" --batch 10 --workers 12

# 先试 100 条
& $py "scripts\judge-batch.py" --limit 100

# 输出：scan/short-verdicts.jsonl（逐条）+ 三份 CSV
```

脚本自动读取 `deepseek-key.txt` 和 `deepseek-key-2..9.txt`，多 key 轮询。
（注意：多 key 只在**不同账号**时有效，同账号共享 QPS 限制。）
